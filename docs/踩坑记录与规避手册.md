## 1. COM 内存 / 无状态铁律

### 1.1 RCW 按对象标识缓存，FinalRelease 会连带销毁他人持有的 RCW（高危）
- **现象**：工具/writer 在 `finally` 里对 `解析出的 sheet` 调 `FinalReleaseComObject` 后，调用方后续任何动态访问抛 `COM 对象与其基础 RCW 分开`。
- **根因**：.NET COM 的 RCW 按底层对象标识（IUnknown 指针）缓存。同一 Worksheet 无论经 `wb.Worksheets.Item[1]` 还是 `application.ActiveWorkbook.Worksheets["dt"]` 解析，都返回**同一个 RCW**。`FinalReleaseComObject` 语义是「销毁该 RCW」而非「减引用」，销毁调用方仍持有的同名 RCW 后，该 RCW 即失效。
- **规避**：真机 harness / 自检器必须**严格无状态**——每次操作前重新解析工作表、用完即放，绝不跨工具调用持有 Worksheet RCW。生产本就是无状态调用（每次重解析）。
- `Marshal.FinalReleaseComObject` 对可能共享/缓存的 RCW 极其危险；`Release` 包装 try/catch 只吞异常不解决问题。

### 1.2 跨程序集释放 COM 用本类私有 SafeRelease
- **现象**：`ExcelContextService.Release` 编译失败。
- **根因**：它是 Excel 程序集的 `internal static`，Addin 程序集无 `InternalsVisibleTo`。
- **规避**：跨程序集释放 COM 用本类私有 `SafeRelease`（`Marshal.IsComObject` + `FinalReleaseComObject` + try/catch），SidebarBridge 已有此法。

## 2. dynamic 与跨程序集访问

### 2.1 dynamic 形参传染命名元组，元素名不可用（RuntimeBinderException）
- **现象**：`var plan=BuildPlan(block,…)` 后访问 `plan.TotalCells` 抛 `“…ValueTuple<…>”未包含“TotalCells”的定义`。
- **根因**：方法接 `dynamic` 形参 → 该调用变动态分派，返回值退化为 `dynamic`，且逐级传染给下游。元组元素名（`TotalCells`/`Name`）**不是运行时成员**，动态绑定器找不到。
- **规避**：在源头把动态调用结果显式还原静态类型（`object[,] block = ReadMatrix(range,…)`）；或对动态结果用真实运行时成员 `Item1/Item2`，勿用元素名。

### 2.2 跨程序集用 dynamic 访问匿名类成员会被拒（RuntimeBinderException）
- **现象**：VerifyPhaseF 用 `dynamic d = it; d.ok` 访问 Addin 内部返回的匿名对象抛 `“object”未包含“ok”的定义`。
- **根因**：`new { name, ok, detail }` 匿名类是**内部类**；而 Newtonsoft.Json 序列化 internal 类型的 public 属性不受影响（反射忽略类型可见性）。
- **规避**：跨程序集读取这类结果统一走 `JsonConvert.SerializeObject(list) + JArray.Parse`，前端直接 `JObject.FromObject(Data)`；不要用 dynamic 导航元素名字段（元组/匿名成员名也不是运行时成员）。前端渲染 tool 卡片对 `Data` 动态取键同理用 JObject。

### 2.3 net48 没有 Dictionary.GetValueOrDefault 扩展
- **根因**：该扩展是 .NET Standard 2.1+ 才有。
- **规避**：新增语法特性前先确认目标框架 net48 兼容性；用 `TryGetValue` 拼初值替代。

## 3. VBA 执行

### 3.1 Ribbon 按钮把执行丢线程池 → WebView2 跨线程崩溃（v1.16.1）
- **现象**：用户点「解释公式/智能填充」毫无反应。
- **根因**：`InjectRibbonPrompt` 用 `Task.Run(() => inject(prompt)...)` 把 SendPrompt 扔到线程池线程；SendPrompt 内部 `Publish` 访问 `WebView2.CoreWebView2`（**仅允许 UI 线程**）→ `CoreWebView2 can only be accessed from the UI thread`。
- **修复**：去掉 `Task.Run`，Ribbon `onAction` 本就在 UI 线程，直接同步 `inject(prompt).GetAwaiter().GetResult()`。
- **规避**：凡是 Ribbon onAction 里执行依赖 WebView2/UI 控件的操作，绝不能丢到线程池线程。先查 `%TEMP%\ExcelAiAssistant.log` 定位「按钮无反应」是否 `InjectRibbonPrompt failed`。

### 3.2 run_vba_snippet 复用常驻草稿模块（v1.19.2 性能+稳定性）
- **现象**：VBA 执行慢（反复重编译），且 Excel 忙碌时抛 `0x80070578 无效的窗口句柄`。
- **根因**：旧实现每轮 `VBComponents.Add(新模块)→AddFromString→Run→RemoveComponent`，触发 VBE 工程反复增删重编译；频繁触碰 VBE 编辑窗口句柄。
- **修复**：在活动工作簿内复用**常驻标准模块 `JYYJHelper`**——已存在则 `DeleteLines(1,CountOfLines)` 清空后重写直接 Run，不再 Remove；首次缺失才 Add 并保留。实测 3 次 run_vba 降到 ~60ms，工作簿内标准模块数恒为 1。
- **坑点**：**VBA 模块/过程名不能以下划线开头**，`module.Name="_JYYJHelper"` 会静默失败导致按名复用退化 → 用 `JYYJHelper`。ScreenUpdating 需注入+Run 全程 off 再恢复；替换时要清空旧 `Option Explicit` 避免重复声明。

### 3.3 工作表名含双引号导致 VBA 字符串注入漏洞
- **现象**：工作表名如 `Sheet"1` 时，注入 `Range("'Sheet"1'!...")` 拆断 VBA 字符串。
- **修复**：注入前按 VBA 规则将 `"` 转义为 `""`。

### 3.4 run_vba_snippet 宏不可用/禁用错误处理（v1.20.0.1）
- **现象**：宏被禁用时返回晦涩的 `VBA_RUN_ERROR`，AI 反复重试。
- **修复**：工程锚定（优先 `ActiveWorkbook.VBProject`，其次第一个工作簿，最后回退 `ActiveVBProject`）、临时设置 `AutomationSecurity=1`（Low）并在结束后还原、新增错误分类 `VBA_MACROS_DISABLED` 并返回明确指引（启用宏或改走内置工具）。

### 3.5 外部进程 Excel 的 VBA 错误弹窗无法被 On Error 探针抑制（v1.20.0.2 实测）
- **现象**：out-of-proc（`Activator.CreateInstance("Excel.Application")` 起的隐藏 Excel）里，探针 `XaiProbe9F2E` 的 On Error **不能阻止 Excel 弹 VBA 模态错误框**，`Application.Run` 永久阻塞（等用户点弹窗）→ harness 假性超时。
- **关键认知**：**探针抑制弹窗只在 in-proc 真实 Addin 里被证实**；out-of-proc 自动化只能验证成功路径与静态护栏，**无法用来证明「无弹窗」**。
- **规避**：真机验证错误拦截逻辑时改为断言纯逻辑护栏（正则），而不是真去运行会报错的 VBA。

### 3.6 VBA 探针首轮瞬态「宏不可用」(HRESULT 0x800A9C68) 需自愈重试（v1.20.0.3）
- **现象**：首轮 `Application.Run(探针)` 抛 HRESULT 0x800A9C68，第二轮才成功。日志表现为「第一轮报晦涩 HRESULT、第二轮才成功」。
- **根因**：模块刚写入/改写后探针未被 VBE 编译器就绪。**该瞬态≠宏禁用**（同会话后续调用曾成功）。
- **修复**：`RunVbaProbeWithRetry`——若判断 `ProbeLikelyUnavailable`（低16位==0x9C68 或消息含 cannot run the macro / may not be available / 宏不可用 / 所有宏都被禁用等）则重追加探针重试一次自愈；真禁用重试也抛、落到 `VBA_MACROS_DISABLED`，无死循环。
- **测试注意**：十六进制 HRESULT 作 InlineData 需换算成**有符号十进制**（int 上限装不下 0x800A9C68）。

### 3.7 失败日志只记 ErrorCode 不记真实错误正文（v1.20.0.3）
- **现象**：失败时日志只写 `VBA_RUN_ERROR`，设置页看不出真正原因。
- **修复**：失败时把 `ev.Result.Data`（如 `VBA 运行时错误 1004: Method 'AutoFit'...`）经 `CompactLogText`（折叠换行+截断300）并入同一行。
- **教训**：诊断类日志必须带**真实错误消息**而非常规错误码。

### 3.8 2D `.Range(...).AutoFit` 静态校验从 suggestion 升为阻断 error（v1.20.0.3）
- **现象**：多行多列矩形 `.AutoFit` 运行时必抛 1004，旧校验只给 suggestion 且 `valid` 仍 true，模型仍带坏代码跑并反复失败。
- **修复**：`RegexVbaAutoFit2D` 命中判 error（阻断），合法 `Rows/Columns.AutoFit` 仅 suggestion；正则做 `public static` 便于前端/测试直接断言。
- **已知保守局限**：单格 `.Range("A1").AutoFit`（单行+单列，合法）也会命中——属**启发式保守阻断**（宁可拦也不让跑坏 2D 写法）。VerifyVbaFix 场景2 的 good/bad 用例刻意避开单格裸写法以免误伤。若要精确需解析区域坐标维数。

### 3.9 独立 Excel 验证 VBA 的稳妥做法
- 真机验证 VBA 走「新建未存盘内存工作簿 + AutomationSecurity=1」最稳；避免中途 SaveAs/重开触发 VBE 模态 / `0x800706BE`。

## 4. 前端 / 侧边栏 / WebView2

### 4.1 前端内联 JS 一个语法错误废掉整个侧边栏（v1.19.4.1，高危）
- **现象**：侧边栏「工作簿: 加载中」永久卡住、所有按钮点不动。
- **根因**：`index.html` 是**一整段内联 `<script>`**，任何一处语法错误让整段脚本解析失败 → 事件绑定全丢 + 初始化不运行。本次根因是对象字面量用**负数作未加引号的键** `{..., -4102:"三维饼图", ...}`——**负数的 `-` 是运算符，必须加引号** `{"-4102":...}`，否则 `Unexpected token '-'`。（JS 对象键可以是标识符/字符串/非负数字面量，负数不行。）
- **规避/验证铁律**：改动 index.html 后必须抽出 `<script>` 正文跑 `node --check`（跳过 `<script>`/`</script>` 行、存为 .js 再校验，不能直接对含标签文件跑）。因 index.html 作为 ManifestResourceStream 内嵌进 Addin.dll，源码改完必须重打包重装，并用 `ReflectionOnlyLoadFrom(已装dll).GetManifestResourceStream("...index.html")` 抽取**已安装 DLL** 内嵌 HTML 再 `node --check`，才能闭环确认修复真的随包部署。

### 4.2 技能标签 / 快捷按钮不显示 ＝ 序列化漏字段（v1.16.3.1）
- **根因**：`SidebarBridge.cs` 的 `GetSkills()` 漏序列化 `skill.Type` 字段，前端拿不到类型信息。
- **修复**：两处序列化对象添加 `skill.Type` 字段。

### 4.3 快捷/技能 chip「点了没反应」= 只填 prompt 不发送（v1.19.5.0）
- **现象**：点 chip 只是把 prompt 填进输入框，不发送，用户得再按一次发送。
- **根因**：`renderQuickRow` 里三类快捷 chip 的 click 只做 `prompt.value=p.prompt; prompt.focus()`，不触发发送。
- **修复**：抽 `runQuick(p){ if(sendButton.disabled)return; prompt.value=p.prompt; send(); }`，三类 chip 统一 click 即发；技能 chip 用同一 `runQuick`（prompt=`/技能名` → 后端 `ApplySkillDirective` 正则 `/(skill|skill:)([\w-]+)`）。
- **真机闭环**：`tools/VerifyQuickChip`（WebView2 + 真实 `SidebarBridge` + 真实 Excel，前端只用 `excelAiBridge` 一个 host 对象名；index.html 必须从 `typeof(SidebarBridge).Assembly.GetManifestResourceStream` 取，不能 `Assembly.GetExecutingAssembly()`）。

### 4.4 WebView2 `ExecuteScriptAsync` 不等待返回的 Promise（协议外坑）
- **现象**：注入脚本返回 Promise 时，运行时直接把 Promise 序列化成 `{}`，`JObject.Parse("{}")` 拿空对象，随后 `title` 为 null 抛 NRE。
- **规避**：向 WebView2 注入的探针脚本一律返回**同步对象**；要轮询/延时就绪，在 **C# 侧循环**调用同步脚本判断，再发同步点击脚本，勿用 JS Promise + setTimeout。

### 4.5 前端异步渲染时序抖动导致固定延时探测 flaky
- **现象**：`Task.Delay(1500)` 后单次探测偶发落在 DOM 未解析完成时刻（元素全 null）。
- **根因**：sidebar 加载 ~174KB index.html + `LoadSkills` 异步重建 DOM，速度随机器漂移。
- **规避**：改为 C# `PollReady` 轮询（250ms×60，等 chip+sendButton+prompt 齐备）再动作。**凡断言侧边栏真实 DOM 的 harness，一律「轮询就绪→再动作」，不要定死 sleep。**

### 4.6 注入脚本 C# 拼接括号易失衡
- **现象**：`((function(){...})())` 开头开两个括号结尾没配平，整段 JS 语法错误 → `ExecuteScriptAsync` 返 `null`（而非抛异常）；`.Trim()` 误写到已闭合调用之后报 CS1003。
- **规避**：拼接完整体观察所成 JS 的括号配平，别只看行内。

### 4.7 WebView2 `ExecuteScriptAsync` 对返回字符串再套引号 → 参数框读取失败（v2.18.6.0，真机+harness 闭环）
- **现象**：参数框点「确认执行」报 `读取参数失败：Error reading JObject from JsonReader. Current JsonReader item is not an object: String`。
- **根因**：`webView.CoreWebView2.ExecuteScriptAsync("JSON.stringify(collect())")` 对返回「字符串」的结果会**再套一层引号**（返回 JSON 编码的字符串字面量，首字符是 `"`），`JObject.Parse` 拿到字符串而非对象 → 报 not-an-object。`collect()` 返回的是 `{ok,values}` 对象。
- **修复**：改为 `ExecuteScriptAsync("collect()")` 直调，让 WebView2 按对象序列化，直接得到顶层 `{...}`。
- **规避**：WebView2 `ExecuteScriptAsync` 的返回——脚本返回**对象**→得到 JSON 对象；返回**字符串**（含 `JSON.stringify` 产物）→ 会被再套一层引号。需要可 `JObject.Parse` 的结构时，让 JS 侧返回对象，不要 Stringify。验证工具 `tools\VerifyParamJson` 用真实 WebView2 双向断言（复现 stringify 失败 + 直调成功）。

### 4.8 Ribbon `getImage` 图标「点一次就消失」：记忆化缓存 + `fOwn=false`（v2.18.6.0，真机验证）
- **现象**：功能区自定义彩色图标，点一次按钮后下次重绘图标变空白/消失。
- **根因**：每按钮每次 `getImage` 回调都 `new` 一个 IPictureDisp 且 `OleCreatePictureIndirect` 传 `fOwn=true`（OLE 接管并销毁传入的 hicon）。Office 点击/重绘释放旧 picture 时销毁该 hicon，下一次重取句柄失效 → 显示空白。
- **修复**：`static ConcurrentDictionary<string,object>` 按按钮 Id 缓存同一份 IPictureDisp 全程持有；`ToPictureDisp` 改 `fOwn=false`，OLE 不销毁 hicon，由缓存/进程生命周期持有。
- **规避**：Ribbon 图标走「记忆化缓存同一 IPictureDisp + `fOwn=false`」两件套；切勿 `fOwn=true`（Office 释放即销毁句柄，缓存复用会拿到悬空图标）。真机验证：连续点击两次按钮，图标应始终彩色可见。

### 4.9 参数框下拉/多选选项空白：camelCase 序列化改写了字段名（v2.18.7.0，harness 闭环）
- **现象**：配置弹窗里所有下拉框、多选 chip 都是空白，没有可选项文字。
- **根因**：后端 `ParamOption` 属性是 PascalCase（`Value`/`Display`），序列化用 `CamelCasePropertyNamesContractResolver` 输出为 `value`/`display`；前端 JS 却读 `o.v`/`o.d`（旧契约）→ 恒为 undefined，选项文本渲染为空。
- **修复**：前端统一改读 `o.value`/`o.display`；并给 `ParamField` 增加 `Hint` 属性，每个字段下方渲染灰字说明（`hintHtml(f)`，multiselect 无 hint 时兜底"点击选择/取消，可多选"）。
- **规避**：凡 C# 对象经 camelCase 序列化注入 HTML 模板，前端必须按序列化后字段名取键，禁止按类属性简写猜。闭环验证：`tools\VerifyParamJson` 加载**真实 ParameterForm.html + 真实 BuildFields 数据**进 WebView2，断言选项文本非空、Hint 23/23、无 undefined 选项。

### 4.10 参数框窗口不能缩放：`FixedDialog` 边框样式（v2.18.7.0）
- **现象**：配置弹窗尺寸固定，拖不动边角，没有最大化按钮。
- **根因**：`RibbonParameterDialog` 构造时 `FormBorderStyle = FixedDialog` 且 `MaximizeBox/MinimizeBox = false`，WinForms 下该样式禁止用户调整大小。
- **修复**：改 `FormBorderStyle.Sizable` + `MaximizeBox/MinimizeBox = true`，设 `MinimumSize = new Size(440, 420)` 防缩放过小界面错乱，初始 `ClientSize = new Size(600, 640)`。
- **规避**：需要用户自调大小的 WinForms 弹窗用 `Sizable`；不要只改 `AutoSize` 而忘掉边框样式。真机验证拖角缩放 + 最大化。

### 4.11 函数库 FX_LIB 数据数组：畸形行 / 重复函数名 / 版本标注错位（v2.19.0.0，node 校验兜底）
- **现象**：函数库面板整页空白/崩溃，或同一函数在多个分类重复出现，或版本徽章标错。
- **根因**：`index.html` 的 `FX_LIB` 是一段**纯数据数组**，手工维护极易出三类问题——① 行元素缺字段、字段数≠8（分类/名/中文名/说明/参数/示例/示例说明/占位公式）；② 函数名重复（如 IFNA 在 `other` 与 `logic` 各一条，列表重复）；③ 畸形残留行（曾出现 `["lookup","TRUe"..""]` 这类半截拼写错误，`..` 非法直接让整段解析失败）。此外版本标注还易与官方引入版本身份不符（如 MAXIFS/MINIFS 实为 2019 但不是 2016）。
- **规避/验证铁律**：改动 FX_LIB 后必须跑 `node tools/validate-fxlib.js`（真实解析数组，检重复/字段数/示例公式合法性 + 版本映射完整性）与 `node tools/check-fx-js.js`（抽 `<script>` 做语法校验）、`node tools/test-fxlib.js`（功能性断言：版本枚举合法、按版本筛选命中、常用分类完整）。三连全绿才算过。新增函数若给了 `FX_VERSION` 版本映射，必须在 `FX_LIB` 有对应条目，否则校验提示"有版本、未收录"。
- **TDZ 致命坑（v2.19.0.0 修复）**：`FX_LIB` 的 `.map()` 构建时即调用 `fxVersionOf(r[1])`，而 `fxVersionOf` 内部读 `FX_VERSION`；若 `const FX_VERSION = {...}` 声明在 `FX_LIB` **之后**，则 `const` 的**暂时性死区（TDZ）**使初始化前访问抛 `ReferenceError: Cannot access 'FX_VERSION' before initialization`，脚本在此中断——`initFxLib()` 永不执行，内置函数库**卡死在"加载函数库…"初始态**，而顶部 JYYJ函数库因走独立异步渲染仍正常显示（表象极具迷惑性）。此类"语法校验/结构校验全绿、运行时却加载失败"只能用运行时冒烟抓。修复：把 `FX_VERSION` 与 `fxVersionOf` 提到 `FX_LIB` **之前**定义，并删除原位重复定义。验证：`node tools/runtime-smoke.js`（vm mock 最小 DOM 从头执行整个 `<script>`，脚本真正跑完到 `initFxLib()` 无异常才算过）。教训：`const` 被 `function` 提升迷惑——`fxVersionOf` 声明后置确实可调用（函数提升），但其**读取的 `const` 变量仍处 TDZ**，最终值未初始化即崩；写"数据常量被后续逻辑引用"的顺序时要一次到位。
- **前端修复必须重建+部署（v2.19.1.0 教训）**：`Sidebar/index.html` 是 **EmbeddedResource 编译进 Addin.dll**，用户在侧边栏加载的是 DLL 内嵌的 html，不是源码文件。因此"改了源码 index.html 校验通过" ≠ "用户已生效"——必须 `dotnet build Addin` 重新把修复后的 html 编进 DLL，再打包部署。排查"修了还不行"的第一动作：对比 `src/.../index.html` 与 `dist/.../app/*.Addin.dll` 的 LastWriteTime，确认 DLL 是否晚于源码（旧 DLL 内嵌旧 html，永远加载老代码）。验证内嵌内容可用字节搜索 DLL 字符串（`[IO.File]::ReadAllBytes` + UTF8 GetString，查 FX_VERSION 位置是否在 FX_LIB 之前 / 是否含新注释）。
- **4.12 前端 mock 双桥：`asyncBridge` 读 `hostObjects.excelAiBridge`（async 子对象），不是 `.sync.`（v2.19.1.0，node 冒烟踩坑）**
  - **现象**：写函数库"示例试运行"定向冒烟时，`fxRunDemoFn` 调 `asyncBridge.PreviewFormula(...)` 报 `Cannot read properties of undefined (reading 'PreviewFormula')`，但整脚本启动冒烟通过。
  - **根因**：`index.html` 头部定义了两个桥——`const bridge = window.chrome.webview.hostObjects.sync.excelAiBridge;`（同步）和 `const asyncBridge = window.chrome.webview.hostObjects.excelAiBridge;`（**异步**，无 `.sync.`）。冒烟 mock 只构造了 `hostObjects:{ sync:{ excelAiBridge }}`，于是 `asyncBridge` 指向 `hostObjects.excelAiBridge` = undefined。启动冒烟不触发 async 方法所以不炸，只有真正调用 `PreviewFormula` 这种仅存在于 async 桥的方法才暴露。
  - **规避/验证铁律**：mock WebView2 桥时**两个子对象都要给**——`hostObjects:{ sync:{ excelAiBridge: bridge }, excelAiBridge: bridge }`。凡前端调到"宿主非同步方法"（Evaluate/异步写入等）的定向冒烟，必须从 4.11 的启动级冒烟升到**注入断言级**冒烟（真实调用新函数，如 `tools/fxdet-smoke.js`），否则运行时问题测不出。

## 5. 测试 Harness（真机验证）

### 5.1 自检器/harness 必须严格无状态（RCW 双坑，v1.19.0）
- 见 1.1。`DiagnosticSmokeRunner` 曾持有 `ws`/`book` 跨多个工具调用，被工具 finally 的 FinalRelease 连带销毁后抛 `InvalidComObjectException`。
- 修复：建簿 / 写 setup / 自检回读 / 关簿**每次重新解析 → 用完即放**。VerifyPhaseF 的 finally 关簿也改为重解析 `app.ActiveWorkbook` 关闭。

### 5.2 每次跑真实 Excel harness 会泄漏独立 EXCEL.exe 进程
- **现象**：`Activator.CreateInstance(progid "Excel.Application")` 起的进程，`excel.Quit()` 不保证终止；多次验证累积大量空标题 EXCEL 实例——它们**锁住安装版 addin.dll**（安装/重打包前必须清掉）且彼此干扰。
- **规避**：每轮 harness 后核查 `Get-Process EXCEL` 并 `Stop-Process -Force` 清理。**提权/被插件占用的实例 `taskkill /F` 报 Access denied 杀不掉**（本机曾残留 PID 42232），只能留在交付前人工处理。

### 5.3 门禁「默认关闭」测试被持久化配置污染（对抗性审查，v1.20.0.3+）
- **现象**：block5「受控执行:默认关闭」五个断言随机器状态漂移变红，且被拦截的工具**真的执行成功**。
- **根因**：`ExcelToolHost` 构造时 `ScriptOptions.Apply(new ControlledExecutionStore().Load())` 从 `%LocalAppData%\XaiAssistant\controlled-execution.json` 加载持久化配置覆盖默认。若上次某会话/测试把 `enabled` 存成 true，`new ExcelToolHost(app)` 默认并非关闭，测试却断言「默认关闭」。产品门禁代码本身正确（`Enabled==false` 优先于白名单检查），是**测试非确定性**缺陷。
- **修复**：block5 前显式 `host.ScriptOptions.Enabled=false` 隔离环境态。
- **教训**：凡是 host 构造会 `Apply(Store.Load())` 的，测试断言「默认值」前必须先显式覆盖，别依赖全局持久化。

### 5.4 `ConfirmationOutcome` 是命名空间级枚举，非嵌套类型（对抗性审查，v1.20.0.3+）
- **现象**：`AgentRunner.ConfirmationOutcome.Confirmed` 编译报 CS0117。
- **根因**：`ConfirmationOutcome` 声明于 `namespace ExcelAiAssistant.Core.Agent` 顶层（与 `AgentRunner` 平级）。
- **教训**：跨程序集改类型引用前，先看该类型是否嵌套，勿想当然挂在类名下。

### 5.5 `Cells.Item[row, col]` 行在前列在后，按地址直觉写反会制造验证假象（v2.0.0.0+）
- **现象**：VerifyWriteRanges 真机验证 write_ranges 回滚时，C# 读 F1 恒为初始值，xlwings 却报已写入 99，误判为「同一实例两个客户端读值不一致」。
- **根因**：harness 用 `ws.Cells.Item[6, 1]` 以为读「F1」，实际参数顺序是 **行在前、列在后** → 读的是 **A6**（第 6 行第 1 列），与 xlwings `range("F1")`（第 1 行第 6 列）根本不是同一单元格。排查了大量实例/Hwnd/PID 对照全一致，纯属坐标 bug 制造的假象。
- **教训**：harness 读写单元格**统一用地址方式**（`ws.Range["F1"]`）或严格 `Cells.Item[row, col]`（先想清行列），避免「F1」直觉与 COM 参数顺序混淆；出现「同一实例读值矛盾」先怀疑坐标/地址写错，再查实例漂移。

### 5.6 真机 harness 结束后要主动清常驻 Python worker
- **现象**：run_python_code/run_python_excel 后残留独立 `python xai_python_worker.py` 进程（常驻 worker），harness 进程退出后仍存活。
- **根因**：`PythonWorkerHost` 常驻 worker 是独立进程，harness 不显式清理则残留。
- **规避**：harness 收尾调 `PythonWorkerHost.ResetWorker()`（杀 worker，下次自动重建）；跑前跑后核对无残留 EXCEL/python。

### 5.7 ChartObjects 集合索引从 1 起 + SERIES 公式拆三段，图表断言两处必踩（v2.0.0.0）
- **现象①**：`ChartObjects().Item(after - 1)` 读新增图表抛 `HRESULT:0x800A03EC`（索引越界）；before=0 时索引 0 非法。
- **规避①**：`ChartObjects` / `Charts` 等 COM 集合**从 1 起**，新增图表在末尾 → 索引用 `after`（总个数），不能用 `after - 1`。
- **现象②**：断言「图表绑定选区 A1:B6」用 `Contains("A1:B6")` 恒失败——实际回读 `Series.Formula` 是 `=SERIES(Sheet1!$B$1,Sheet1!$A$2:$A$6,Sheet1!$B$2:$B$6,1)`，**Excel 把选区拆成名称/分类轴/数值轴三段**（表头单格、分类区间、数值区间分开）。
- **规避②**：按拆分格式断言——分类轴 `$A$2:$A$6` 与数值轴 `$B$2:$B$6` **同时**出现即证明绑定选区，勿匹配整块 `A1:B6`。
- **附带**：C# 条件表达式两分支类型不同（`string` vs `double`）报 CS0173，需显式 `(object)` 强转。

### 5.8 xlwings `chart.api` 是二元组，设标题须走 `api[0].Chart`（v2.0.0.0）
- **现象**：模板 `chart.api.Chart.HasTitle = True` 抛 `'tuple' object has no attribute 'Chart'`；`chart.api[1].SetElement(3)` 抛 `com_error(…'发生意外。')`（E_FAIL）。
- **根因**：xlwings `Chart.api` 返回 **`(ChartObject, Chart)` 二元组**（元素为 `COMRetryObjectWrapper`），不是单一对象——`chart.api.Chart` 直接访问元组属性必然失败。`api[1].SetElement` 在 ChartObject 上调用 SetElement 不适用（SetElement 是 Chart 方法），且网上例（`api[1].ChartTitle`）为版本差异。
- **正确写法**（真机探测确认）：`ch = chart.api[0].Chart`（ChartObject→Chart）后 `ch.HasTitle = True; ch.ChartTitle.Text = str(标题)`；回读用 C# 侧 `ChartObjects.Item(n).Chart.ChartTitle.Text`。

### 5.9 gate Excel 泄漏检查撞机器并发 Excel COM 测试的环境冲突（v3.8.1.77）
- **现象**：gate 在 Excel 真机步反复报「泄漏宿主进程 excel.exe(pid=…)」，清掉又冒新 PID；核实例程命令行全部是 `EXCEL.EXE /automation -Embedding`（探针类 out-of-proc 实例，非用户有窗口实例）。
- **根因**：机器上另一处工作负载（`D:\execl-mcp` 的 ExcelMcp.Core.Tests `dotnet test`）正在并发跑 Excel COM 测试，持续拉起/退出 /automation Excel 实例——gate 的泄漏检查在其检查时刻总会撞上别人的实例，属环境冲突而非本批代码泄漏（本批改动为纯逻辑+前端，不触 COM）。
- **处置**：①先核实实例归属（命令行含 `/automation -Embedding` 即探针/自动化类；有窗口的 EXCEL.EXE 是用户实例绝不可动）；②确认冲突方归属后**等它跑完**（轮询 `Win32_Process` 直到无 EXCEL.EXE），清理残余后重跑 gate 即全绿；③不可盲目 Stop-Process 别人正在使用的测试进程——可能毁掉用户另一会话的工作。
- **教训**：真机门禁的 Excel 泄漏断言隐含「机器级 Excel 独占」假设；并发开发环境下 gate FAIL 先查并发工作负载归属，勿先怀疑本批代码。
- **教训**：xlwings COM 包装属性（`.api`）结构随版本变化，写死 `.api.Chart` 前先探测真实结构；探测用独立 `xw.App(visible=False)` 脚本最直接，但**必须确保 `app.quit()` 生效**——否则残留隐藏 EXCEL 进程（无窗口标题），需 PID 强杀清理。

### 5.9 xlwings `sheet.range("'另一表'!A1:B6")` 不接受跨表地址（v2.0.0.0，审查 VPC-7 挖出）
- **现象**：活动表≠数据表时，模板 `sht.range("'Sheet1'!A1:B6")` 抛 `pywintypes.com_error…0x800A03EC`。而活动表恰为 Sheet1 时**不报错**——同一行代码对错只在活动表不同，隐蔽性极强。
- **根因**：xlwings `Range` 经 `Worksheet.Range(Cell1)` 转发，**`Worksheet.Range` 不接受跨工作表地址**（addr 含 `!` 时 Excel 抛意外）；同表地址才解析成功。此前 VPC-1~6 全在「活动表=数据表」场景验证，掩盖了此缺陷。
- **修复**：模板用 `re` 解析 `'表名'!区间` 地址，定位到 `xw.books.active.sheets[表名]` 再取区（跨表画图），无表名才用活动表 `sht.range`。
- **教训**：验证「选区→画图」链路的 harness 必须补**跨表场景**（激活表≠数据表），只在单表场景通过不代表正确；审查阶段新增 VPC-7 正是为暴露此类隐蔽缺陷。

### 5.10 `Worksheets.Add()` 默认插到活动工作表之前，表索引≠预期的坑（v2.0.0.0）
- **现象**：VPC-7 建第二张表后命名为 "Sheet2"，但新增表插到当前活动表**之前**，导致 "Sheet2" 索引变 1，断言 `ChartObjects.Item(2)` 落错表（读到的还是 Sheet1 上已有图表）。
- **根因**：`Worksheets.Add(Before, After)` 两参数皆可选，**默认 `Before=ActiveSheet`**——新表插到活动表前。不指明 `After` 时索引不可预测。
- **规避**：要追加在末尾用 `Worksheets.Add(Missing.Value, wb.Worksheets.Item(count))`（After:=最后一张），或显式 After 定位；harness 先固定 `sheetIndex=count+1` 再做表相关断言。

### 5.11 反射读取 `ValueTuple` 数组元素：公开字段而非属性（v2.0.0.0）
- **现象**：VerifyVerifyChart 反射读 `ChartTypeMap`（`ValueTuple<int,string,string>[]`）时 `GetProperties()` 返回空、`GetProperty("Item2")` 取不到 Family。
- **根因**：.NET 的 `System.ValueTuple\`N` **以公开字段（Item1/Item2/…）暴露成员，没有公开属性**；`ValueTuple` 的字段/属性是通过编译器把 `(int XlType, string Family, string Name)` 别名映射到 Item1/2/3，运行时只有字段。
- **规避**：反射读 ValueTuple 元素用 `GetField("ItemN")`（而非 `GetProperty`）；先 `GetProperties()` 诊断首元素成员名再取。
- **附带**：自检语义——`verify_chart` 类型不符 → verdict 变 `mismatch`（或 `+mismatch`）；系列数不符 → **只追加「系列数量与预期不符」issue、不改 verdict**（verdict 仍 ok）；标题不符 → `title`；数据源不符 → `source`。harness 断言须按此语义写，勿臆断。

### 5.12 out-of-proc 动态 COM 的 `Close/Quit` 收尾会进程级硬故障，harness 按 PID 强杀兜底（v2.0.0.0 自动自检真机验证）
- **现象**：`tools/RealMachineVerify` harness 测试全部通过后，收尾 `workbook.Close(false)`（dynamic 调用）触发进程级硬故障——「由于 Exception.ToString() 失败，因此无法打印异常字符串」，`== 结果 ==` 汇总行打不出、退出码被吞。
- **根因**：out-of-proc 动态 COM 调用进入退出路径时发生 fail-fast/损坏状态异常，普通 `catch` 甚至 `[HandleProcessCorruptedStateExceptions]` 都拦不住（异常连 ToString 都无法构造）。`try/catch` 包裹无效，进程直接终止。
- **规避**：harness 收尾**不做 Close/Quit 动态 COM 调用**——工作簿是未存盘草稿、无保存价值，启动 Excel 前快照已有 PID，结束时对新 PID `Process.Kill()` 兜底（即 §5.2 的思路代码化）；用户自己的 Excel 进程不受影响。
- **附带**：真机 harness 抓到了单测漏掉的真缺陷（`sort_range` 自动自检计划漏传必填 `address`，verify 报「缺少必填参数」）——**纯逻辑单测只断言 expected_* 字段，必填上下文参数（address/sheet）要靠真机回读才能暴露**；新映射进真机 harness 是必修课。

### 5.13 断言子串别写 `Assert.True(x.EndsWith/Contains(...))`，xUnit2009 分析器直接编译报错（v2.19.4.0）

- **现象**：`TreatWarningsAsErrors=true` 下写 `Assert.True(result.EndsWith("…"))` 提交构建，编译器报 `error xUnit2009: Do not use Assert.True() to check for substrings. Use Assert.EndsWith instead.`（`Contains` 同理用 `Assert.Contains`），测试无法编译、门禁中止。
- **根因**：xUnit 分析器把「用 `Assert.True(布尔表达式)` 断言子串/后缀」判定为可读性反模式，强制用专用断言 API。
- **规避**：一律用 `Assert.EndsWith(expected, actual)` / `Assert.Contains(substring, actual)`（参数顺序是**期望在前、实际在后**）。顺带注意断言字符串匹配到的是**字面真实值**：`NoCr` 这类多语句测试别凭直觉写初值，先跑一遍看 Actual，再固化为期望（v2.19.4.0 补 `NoCr` 测试时三次踩空：`\r\n` 折行实际是双空格、`.Trim()` 会清掉全部首尾空白、行内缩进保留）。

## 6. 打包 / 安装 / 发布

### 6.1 安装时 addin.dll 被 Excel 占用锁死
- **现象**：install 脚本 Copy-Item 在 Excel 运行且加载了加载项时抛 IOException。
- **规避**：装新版本前必须先关 Excel（手动保存退出，勿强杀以免丢未保存数据）。

### 6.2 发版只改了 dist，没重装 addin → 用户 Excel 仍是旧版（「版本不对」根因）
- **现象**：回归 harness 全 PASS，但用户「关于/版本」仍显示旧版本（如 1.20.0.1）。
- **根因**：Verify* 系列 harness 用 `typeof(SidebarBridge).Assembly.GetName().Version`，取自各工具 **bin 输出目录的副本**，并非用户 Excel 实际加载的**安装版**（`%LOCALAPPDATA%\XaiAssistant\app\{x64,x86}\ExcelAiAssistant.Addin.dll`）。只构建进 dist 却没跑安装脚本，安装位仍是旧版。
- **修复/规避**：发版必须重新跑安装脚本：`powershell -File tools\install-xai.ps1 -Architecture x64 -Source "dist\JYYJ助手-<ver>-x64\app"`（Auto 自动探测架构）。安装会 Copy 到安装位 + 按新版本号重注册 HKCU COM 版本子键 + 写 Excel Addin LoadBehavior=3。安装前确认无残留 EXCEL。
- **验证加载是否来自安装位**：看 `%TEMP%\ExcelAiAssistant.log` 的 `LoadSkills … builtIn=C:\…\XaiAssistant\app\x64\skills` 路径即安装目录；**harness 自报版本不能当作交付证据**。

### 6.3 EXE 安装器打包流程（Inno Setup 6，供小白一键装）
- 模板：`tools\installer\JYYJ助手-{ver}-{x64|x86}.iss`。发版步骤：
  1. 构建 `dist\JYYJ助手-{ver}-{x64,x86}\app`，**核对 Addin.dll 版本必须=ver**（`FileVersionInfo`）；
  2. 从上一版 .iss 复制 {ver}.iss，**只改 `#define AppVersion` 与 `#define PkgSrc` 两条宏**，其余不动；
  3. 编译：`"C:\Program Files (x86)\Inno Setup 6\ISCC.exe" <xxx.iss>`，产物输出到 `dist\installer\JYYJ助手-{ver}-{arch}-Setup.exe`。
- 要点：注册逻辑不在 .iss，而在随包分发的 `register-{arch}.ps1`（[Run] 段静默执行，**动态读安装版 Addin.dll 程序集版本写 COM 版本子键**，故无需每版改脚本）；[Code] `InitializeSetup` 用 FindWindow('XLMAIN') 检测 Excel 运行，占用则弹「先关 Excel 再重试」；`PrivilegesRequired=lowest` 免管理员按用户注册。
- 架构写注册表视图：x64 用 `{sysnative}` 起 64 位 PS 写 64 位视图；x86 用 `{sys}`=SysWOW64 起 32 位 PS 写 32 位视图。
- iscc 编译仅有的提示「[UninstallRun] 缺 RunOnceId」无害可忽略。

### 6.4 开发机 Excel 实际从 bin\x64\Release\net48\win-x64 加载，不是 AppData（v2.18.7）
- **现象**：源码/部署目录都更新了新 Ribbon.xml，重启 Excel 后功能区仍是旧按钮（无新控件、无新 tooltip），反复「部署→验证」都像没生效。
- **根因**：开发机上 Excel 加载的 Addin 来自 `src\ExcelAiAssistant.Addin\bin\x64\Release\net48\win-x64\`（日志 `LoadSkills … builtIn=D:\…\bin\x64\Release\net48\win-x64\skills` 为证），而注册表 CodeBase 指向 `%LOCALAPPDATA%\XaiAssistant\app\x64\` 只是安装位。两者不同步时，**只更新 AppData 无效**。
- **修复/规避**：改 Ribbon.xml / Addin 代码后，**同时**把 3 个业务 DLL（Addin/Excel/Core）从 `bin\Release\net48` 复制到**两个位置**：
  1. `src\ExcelAiAssistant.Addin\bin\x64\Release\net48\win-x64\`（开发机实际加载位）
  2. `%LOCALAPPDATA%\XaiAssistant\app\x64\`（注册表 CodeBase 安装位）
  并在每次验证前先 `Get-Content $env:TEMP\ExcelAiAssistant.log -Tail` 确认 `builtIn=` 指向的目标，或用「新增一个实验按钮看是否出现」判定当前加载的是哪份构建。
- **提示**：`dotnet build` 只写 `bin\Release\net48`；`-p:Platform=x64` 才写 `bin\x64\Release\net48\win-x64`。开发时若从未跑过 x64 平台构建，`win-x64` 目录是**旧产物**，最容易成为「幽灵加载源」。

### 6.5 打包版本号三处同步改由 package-xai.ps1 -BumpVersion 自动完成（v2.18.8 引入）
- **背景**：发版 SOP 要求 `Addin.csproj`（Version+InformationalVersion）、`README.md`、`tools\installer\JYYJ助手-<ver>-Setup.iss` 三处版本号一致，人工改易漂移。
- **做法**：`tools\package-xai.ps1 -BumpVersion` 从 csproj 读当前版本，按 `-BumpPart`（默认 Patch）递增并**自动同步三处**：
  1. csproj 的 `<Version>` 与 `<InformationalVersion>`（UTF-8 BOM 写回）
  2. README.md 的 `vX.Y.Z.W`（UTF-8 BOM 写回）
  3. 复制最新 iss 为 `JYYJ助手-<新版本>-Setup.iss`，替换 `#define AppVersion`、`PkgSrc64/86` 路径、首行注释版本号（UTF-8 无 BOM 写回）
- **规避要点**：
  - `-BumpVersion` 与 `-Version` 互斥；目标 iss 已存在则拒绝覆盖（防误毁旧版）。
  - 递增后段清零：Patch → `2.18.8.0`，Build → `2.18.7.1`，Major → `3.0.0.0`。
  - **PS 5.1 写文件必须显式指定编码**：csproj/README 用 `UTF8Encoding($true)`（带 BOM），iss 用 `UTF8Encoding($false)`（无 BOM，Inno Setup 读 UTF-8 无 BOM 正常）。用 `Set-Content -Encoding UTF8` 在 PS5.1 会带 BOM，iss 中文字符可能被 Inno 误读。
  - 验证闭环：跑 `-BumpVersion -SkipReleaseGate -SkipBuild` 看递增日志 → 核对三处 → ISCC 编译新 iss 产出 Setup.exe → 恢复原版本清测试产物。

### 6.6 打包自动升版缺 Inno 编译 → 现版本无安装器 exe + 回归护栏两个坑（v2.18.8 审查修复）
- **现象**：`package-xai.ps1 -BumpVersion` 只做了版本同步与分发包/zip，**从未调用 Inno Setup（ISCC）**，安装器 exe 需人工编译——曾有版本产出了 dist 包却缺 `*Setup.exe`、且无任何提示。
- **修复**：`Invoke-InnoCompile` 自动编译 + `Find-InnoSetup` 探测（`-ISCCPath` → `$env:ISCC_PATH` → PATH → 常见安装目录）。编译后按 **fail-closed 铁律查产物实体**：ISCC 返回 0 不代表 exe 存在（OutputDir/命名任何偏离都会静默丢产物），`Test-Path` 过才打印成功，否则抛「Inno 返回成功但未找到产物」。另由 `-SkipInstaller` 逃生。
- **坑1 · 回归夹具失效**：`verify-versionbump.ps1` 曾 `Copy-Item" scripts\installer\JYYJ助手-2.18.7.0-Setup.iss"`，但历史 iss 会被移入 `archive\`，版本推进后硬编码旧版本文件不存在 → 回归直接抛文件不存在、恰在你需要验证时护栏是坏的。**改法**：沙盒内自建最小 iss 夹具（含 AppVersion/PkgSrc64/86/首行注释），不再依赖任何真实历史文件。
- **坑2 · `$env:ProgramFiles(x86)` 裸写是运行时错误**：PS 会把它解析为读 `$env:ProgramFiles` 后把残留 `(x86)` 当子表达式作用于字符串值。必须写花括号形式 `${env:ProgramFiles(x86)}`。
- **坑3 · PS5.1 读无 BOM 文件里中文串会乱码**：临时探针 `.ps1` 无 BOM 时，`JYYJ助手` 等中文字面量被按 GBK 解码成乱码路径 → `Test-Path` 恒 False、误判产物缺失。**含中文的 .ps1 必须存 UTF-8 BOM**（同 §全局红线）。
- **验证**：`tools\verify-versionbump.ps1` 增至 31 断言（含 Find-InnoSetup 显式命中/路径不存在抛错、Inno 前置守卫、落产物→通过、返回 0 无产物→fail-closed 抛错），全部 fake iscc 沙盒跑通；真机用真实 ISCC 编译 2.18.8.0 exe 端到端通过。
- **坑4 · 替换未命中不报错 → 版本号静默漂移（v2.18.9 审查加固）**：`-replace` 匹配不到时**不报错、只静默不替换**。此前若 csproj 缺 `<InformationalVersion>` 或 README 版本号非 `v` 前缀，升版会静默同步不完整、三处漂移却毫无提示。**改法**：`Sync-VersionFiles` 三个替换段各加 **fail-closed 守卫**——替换后分别校验 csproj 同时含 `<Version>$newVer</Version>`+`<InformationalVersion>$newVer</InformationalVersion>`、README 含 `v$newVer`、iss 不含旧版本号且 `AppVersion` 已替换，任一未命中即 `throw` 中止，不落盘半成品。**教训**：凡用 `-replace` 同步多处关键配置，必须补"替换后目标已达标"的断言，别信正则"应该匹配了"。

### 6.7 离线完整版安装器：Inno [Code] 检测 WebView2 的三个坑（v2.19.4.0 实测闭环）
- **背景**：新增 `JYYJ助手-<版本>-Setup-离线完整版.iss`（捆绑 .NET 4.8 + WebView2 Standalone x64，PrepareToInstall 检测缺失即提权静默安装）。首版静默试装在本机（已装 WebView2 152.x）误判「缺 WebView2」→ 触发提权安装 → 被拒 → 安装中止（退出码 7）。
- **坑1 · WebView2 注册键在 32 位视图，不在 64 位视图**：per-machine 运行时键由 32 位 EdgeUpdate 写入，位于 `HKLM\SOFTWARE\WOW6432Node\Microsoft\EdgeUpdate\Clients\{F3017226-FE2A-4295-8BDF-00C3A9A7E4C5}`（`pv`=版本号）；**64 位视图下无此键**。检测须读 32 位视图——Inno 32 位安装器的 `HKLM` 常量即 32 位视图（天然读 WOW6432Node），写 `HKLM64` 反而查不到；另补 `HKCU`（per-user 安装）双视图兜底。与微软官方检测脚本口径一致。
- **坑2 · [Code] 段字符串里 GUID 花括号 `{{` 转义歧义**：初版把 `'{{F3017226-…}'` 写成 const，实测三视图**全**查不中（连本应命中的 32 位视图也 False）——ISPP 对 `{{` 的转义在 [Code] const 中不可依赖。**改法**：const 只存基址与裸 GUID 两段纯文本，查询前在函数体内用 `Chr(123)`/`Chr(125)` 拼花括号，彻底绕开预处理歧义。
- **坑3 · 版本号同步点从 3 处变 N 处**：新增离线完整版 iss 后，`package-xai.ps1` 原来硬编码单个 `-Setup.iss`（升版只复制它、编译只编它）会造成离线 iss 版本漂移。**改法**：升版与 `Invoke-InnoCompile` 均改为遍历 `JYYJ助手-<版本>-Setup*.iss`（产物名 = iss 文件名去扩展），任一缺失/编译失败 fail-loud。**教训**：每新增一个含版本号的发布文件，同步逻辑必须从"点名"改为"通配遍历"，否则下一个版本必然漂移。
- **验证**：静默试装两轮（第一轮抓出坑1/2 → 修复 → 第二轮 EXIT=0，三个加载项键 LoadBehavior=3，无需重启）；`verify-versionbump.ps1` 升版回归 31 断言全过。

### 6.8 register-auto CLSID 键缺花括号 = 干净机器必报「运行错误」（v2.19.5.0 真机闭环抓出的产品级根因）
- **现象**：用户侧 Excel 2024 装完即弹「加载 COM 加载项时出现运行错误」；开发机却从不复现。
- **坑1 · CLSID 键路径缺花括号**：`register-auto.ps1` 的 `Register-ComClass` 写 `Software\Classes\CLSID\$Guid`（**无花括号**），而 Excel 按 `CLSID\{GUID}` 读取 → 写入的全部 CLSID 键都是无效死键。干净机器上：Addins 键在（LoadBehavior=3）→ Excel 找不到带括号 CLSID → **必然报运行错误**；开发机因构建管道注册过带括号键而被掩盖。`unregister-all.ps1` 的键路径带括号，卸载反而正确。**改法**：统一 `Software\Classes\CLSID\{$Guid}`。**教训**：注册表键名与读取方（Excel/mscoree）逐字符对齐，"能写进去"不等于"读得到"——必须在无开发注册残留的干净视图上验证。
- **坑2 · 运行中的 Excel 会把注册回写为旧路径（mscoree COM shim 自愈）**：只要有 Excel 实例以旧注册启动过，安装器/脚本写入的新 CodeBase 会在毫秒级被回写为该实例当前加载的程序集路径（实测：register-auto 输出 REGISTERED dir=安装目录，1 秒后回读仍是开发路径；杀掉 Excel 后写入即稳定）。**推论**：用户「重装也修不好」的常见根因就是 Excel 没关干净。**改法**：安装说明第零步「先关全部 Excel」；诊断工具新增 Excel 进程检测并给出对应处置建议。
- **坑3 · 支持脚本编码三件套**：PowerShell 5.1 读 **无 BOM UTF-8 的 .ps1 按 ANSI 解析**（中文必坏）→ 必须 UTF-8 **带 BOM**；.cmd 控制台中文用 **GBK**；Win7 记事本对无 BOM 的 .txt 乱码 → txt 也带 BOM。`Get-Content -Tail` 等 PS3+ 参数在 Win7 PS2.0 会炸，诊断类脚本用 `Select-Object -Last` 替代。
- **附**：诊断工具自身 COM 探测会拉起自动化 Excel 实例，侧边栏在无 UI 自动化环境可能初始化失败 → Excel 把面板类加载项记为 LoadBehavior=2。属探针副作用，报告中已加注说明，勿当真故障。
- **坑4 · `tasklist /FI` 过滤器可靠性不足（v2.19.5.0 二次审查发现）**：iss 的 Excel 运行检测最初用 `tasklist /FI "IMAGENAME eq EXCEL.EXE"`，本机实测同一时刻 `/FI` 过滤 **0 命中**、无过滤全量输出却能 grep 到该进程——本地化系统/重定向场景下 /FI 可能静默失灵，防线漏报。**改法**：`tasklist /NH > file` 全量输出后按名搜索（数百行、每装一次只跑几次，性能可忽略）。**教训**：依赖外部工具过滤参数的检测逻辑，必须与无过滤基线做交叉验证。
- **坑5 · 升级/卸载路径的注册残留自愈（v2.19.5.0 二次审查发现）**：坑1 修复只管"新写入"，2.19.4.0 及更早用户注册表里的无括号死键会**永久残留**误导排查。**改法**：`register-auto.ps1` 注册前、`unregister-all.ps1` 卸载时都按 GUID 清理无括号键（`DeleteSubKeyTree($g, $false)` 吞不存在异常），老用户覆盖安装一次即自愈。另：register-auto 对 ARM64 Excel（PE 头 0xAA64）fail-loud 文案改为明确"暂不支持 ARM64"（Addin 是 AnyCPU 可加载，但 SQLite.Interop 为 x64 原生，ARM64 确实不可用）。
- **验证**：修复后干净视图复测（删除全部无括号死键 → register-auto 重写 → 带括号键 CodeBase=安装目录 ✅）；静默试装 2.19.5.0 成功；安装目录诊断报告结构全绿。
- **二次审查追加验证（同日）**：人工植入无括号垃圾键 → unregister-all 清理 ✅、register-auto 注册前自愈清理 ✅（CodeBase=安装目录、LB=3）；`verify-versionbump.ps1` 31 断言 RC=0；重编双安装器后静默试装日志 0 Error；**教训：验证必须确认被测对象是最新产物**——曾误跑安装目录旧副本得出"清理未生效"的假阴性（脚本用 `$PSScriptRoot` 定位，源码目录无 app 目录时 fail-loud 是正确行为）。

### 6.9 沙箱/脚本源 shell 缺 Windows 核心环境变量 → NuGet「Value cannot be null (Parameter 'path1')」（2026-09-08 工具链恢复时定位）
- **现象**：本机（Agent 沙箱的 Git Bash 会话）`dotnet restore` / `dotnet nuget locals` 一律报 `error : Value cannot be null. (Parameter 'path1')`（NuGet.targets），此前多轮误判为 SDK/NuGet 缓存损坏，换 NUGET_PACKAGES/DOTNET_CLI_HOME 均无效。
- **真根因**：该 shell 环境里 `APPDATA`、`PROGRAMDATA`、`ALLUSERSPROFILE`、`SystemRoot`、`windir`、`COMSPEC`、`ProgramFiles`、`ProgramW6432`、`ProgramFiles(x86)` **全部为空**。NuGet 解析用户级（%APPDATA%\NuGet）与机器级（%ProgramFiles(x86)%\NuGet\Config）配置路径时取到 null → path1 异常。`printenv | wc -l` 只有 83 个变量，与正常 Windows 终端差一截。
- **排查口诀**：先 `dotnet nuget locals all --list`——它比 restore 更轻，能最快复现路径解析问题；再 `env | grep -iE "appdata|programdata|systemroot|programfiles"` 对照正常环境做差集。
- **改法（bash 会话内一次性补全环境块）**：
  ```bash
  export APPDATA="C:\\Users\\iamly\\AppData\\Roaming" LOCALAPPDATA="C:\\Users\\iamly\\AppData\\Local" \
    PROGRAMDATA="C:\\ProgramData" ALLUSERSPROFILE="C:\\ProgramData" SystemRoot="C:\\WINDOWS" \
    windir="C:\\WINDOWS" COMSPEC="C:\\WINDOWS\\system32\\cmd.exe" \
    ProgramFiles="C:\\Program Files" ProgramW6432="C:\\Program Files"
  env "ProgramFiles(x86)=C:\\Program Files (x86)" dotnet restore ExcelAiAssistant.sln -c Release
  ```
- **坑1 · bash `export` 不接受 `ProgramFiles(x86)` 这种非法标识符**（`not a valid identifier`），必须用 `env "ProgramFiles(x86)=..." <命令>` 前缀方式注入。
- **坑2 · Agent shell 状态不跨命令持久**：export 只在同一条命令内有效，每条 dotnet 命令都要带完整环境块（或写成前缀函数）。
- **验证**：补环境块后 `nuget locals` 正常列出 4 个缓存路径 → `dotnet restore` 成功（1.88s）→ `dotnet build -c Release` 0 警告 0 错误 → 单测 872/872 通过 → 真机 harness 80/80 通过 → C# 二进制归一 2.19.6.0（grep -a 断言 x64/x86 双命中）→ ISCC 双安装器重编 RC=0 → 静默试装 0 Error + CLSID Assembly=2.19.6.0 + CodeBase=安装目录 + 三 Addins 键 LB=3 + 无括号垃圾键 0 残留。
- **坑3 · Agent PowerShell 工具沙箱无法 spawn dotnet**（同日发现）：即使 PATH 含 `C:\Program Files\dotnet\`、绝对路径直调也**无任何输出**（进程被静默拦截）。绕过：全部构建/打包流程改由 Bash 执行（dotnet 直接可用）；PowerShell 工具仅保留纯文件操作。另：Bash `export` 不接受 `ProgramFiles(x86)` 非法标识符，用函数包装 `env "ProgramFiles(x86)=..." dotnet "$@"` 注入。

### 6.10 守卫/探针类代码对 WPS 工作表做 FinalRelease → 外部持有人 RCW 分离（M17 真机实证，2026-09-09）
- **现象**：M17 保护态守卫探针"枚举命中项读完后 FinalRelease"，WPS 真机里 harness 持有的同名工作表 RCW 被连带分离，后续 Unprotect 报「COM 对象与其基础 RCW 分开后就不能再使用」，解保静默失效、守卫负向用例全绿但收尾断言挂掉。
- **根因**：COM RCW 按 IUnknown 身份缓存——同一底层对象在不同代码路径取到的引用共享同一 RCW；"谁最后拿到谁释放"不成立，释放权无法界定时只有一条路：不释放。
- **改法**：只读探测类代码（读 Name/ProtectContents 等）对 Workbook/Worksheet 级对象**零 FinalRelease**，交 GC 回收；真机闭环里加"跨调用 RCW 存活"断言（解保后写入恢复 OK 即覆盖）。详见 docs/WPS工具兼容差异清单.md「RCW 身份共享」条目。
- **口诀**：探测不释放、短命仅子对象、拿不准就交 GC。

### 6.11 安装器"管理员也杀不死宿主"：PR=lowest 永远降权 + 跨 silo 僵尸进程（M17.5 真机实证，2026-09-09）
- **现象**：用户以管理员身份运行安装包，强杀宿主仍失败，报「自动关闭失败：已多次强制结束，仍有 Excel / WPS 进程存活」。
- **根因 1 · Inno `PrivilegesRequired=lowest` 永远以普通权限运行**：即使右键"以管理员身份运行"，Inno 也会降权重启（安装日志 `User privileges: None` 实证）。旧弹窗指引"右键管理员运行"完全无效——**提权唯一正路 = `ShellExec('runas', ...)` 逐动作发起 UAC**，交互模式下提权前应弹窗预告，避免用户错过 UAC。
- **根因 2 · 跨 silo 僵尸进程任何权限都杀不掉**：真机 harness（COM/DCOM 拉起的 EXCEL.EXE）在 harness 进程被 SIGTERM/异常中断时，`KillSpawnedExcel` 兜底静默失效，遗留进程报「没有此任务的实例在运行」（注意：不是"拒绝访问"），tasklist 能看到但 taskkill 杀不掉、tskill 在 Win11 已移除、Task Manager 同样无解——**只有重启能清**。此类遗留会锁死用户后续安装。
- **改法**：① iss 普通 3 轮 taskkill → `ShellExec('runas')` UAC 提权限强杀，击杀名单补 `wpsoffice.exe`（WPS 2019+ 守护，单杀 et.exe 会被拉起）；② 击杀输出持久化到 `%LocalAppData%\XaiAssistant\logs\hostkill.log`（写 {tmp} 安装结束即删，失败后无据可查）；③ 失败弹窗按真实原因归因（含"服务/自动化拉起 → 重启后安装"）；④ **gate.py 真机步前快照宿主进程、步后 `assert_no_host_leak` 断言无新增泄漏**——泄漏当场亮红，堵死 harness 中断静默遗留的通路。
- **验证技巧**：杀进程逻辑不能靠沙箱内 taskkill 验证（沙箱会 SIGTERM 拦截），必须实跑安装器本体；诱饵宿主用 `copy cmd.exe et.exe` + `/C ping -t 127.0.0.1` 保活（notepad 改名会立即退出、`cmd /K` 读到 EOF 也会退出）。

## 7. 工具实现与参数契约

### 7.1 create_excel_chart 的实参契约
- 必填 `source_address`；可选 `chart_type`（如 `scatter`→`xlXYScatter`/-4169）、`title`、`anchor`、`sheet`。
- **没有** `data_range/dest_range/type`。凡实机/自检调它务必用前者，否则 Required 缺失即抛异常致失败（自检图表项曾因传错键名而恒定失败）。

### 7.2 write_excel_range 形状硬失败致整轮写入被打回（v1.19.1）
- **现象**：AI 对区域形状的估计常有裁剪级偏差（如 B6:G17 12×6=72 格却给 78 格），硬失败让 write 主路径被 AI 放弃、只能换 import_markdown/VBA 兜底。
- **修复**：`RefitToRegion` **按行优先拟合**——值多截断到区域、值少区域剩余格清空（区域替换语义，与等形一致），不再返回 SHAPE_MISMATCH，返回 Data 加 `shape_refit` 标记。另在 `NormalizeValues` 加 `TryParseJsonMatrix`：`values` 是合法二维 JSON 数组字符串时自动解析展开，修掉「整段落进单格（written_cells=1）」。
- 消极测试三项：5格写进2格→截断；2格写进5格→补齐清空；JSON字符串→2x2展开。

### 7.3 format_excel_range 需宽容解析非标准参数（v1.19.3.1）
- **现象**：`Convert.ToInt32(fontColor)`、`Convert.ToBoolean(bold)` 对 AI 传入的十六进制颜色串（`#1F4E78`）或中英文布尔（`是`/`yes`）抛 `FormatException`。
- **修复**：`TryParseColor`（支持 Excel int / `#RRGGBB` / 中英文颜色名）和 `TryParseBool`（1/0、true|false|yes|no|on|off、是|否|对），解析失败跳过该参数并记录，工具仍返回成功，避免整轮调用失败。

### 7.4 跨程序集/JSON 匿名结果读取统一走 JsonConvert
- 见 2.2：工具返回的匿名对象 `Data` 用 `JArray.Parse(SerializeObject(...))` 或 `JObject.FromObject(Data)`；不要用 dynamic 导航成员名。

### 7.5 dedup_range 的 columns 参数契约是列号数组（JArray）
- 传单个 int 会被忽略从而退化为整行去重；真机断言须传 `new JArray { n }`。

### 7.6 数据加工五工具立即释放
- sort/dedup/find_replace/transpose/cond_format 读完整块后立即先 `Release(range/sheet)` 再交给 writer（与 SortRange 统一），避免 writer 与 finally 双重 FinalRelease 的竞态噪音。

### 7.7 AI 研判自检取代演示三件套（v1.19.x）
- 一键自检不再建临时簿跑固定写入/图表/VBA，而是 `RunDiagnosticAdjudication` 扫描 `DiagnosticsLog.Query(600)` 真实日志 → `ExtractLogIssues`（错误模式正则）+ `CountToolEvents`（正则 `工具\[X\] ok/fail`，注意连字符转义）+ `ProbeChartTypeMismatch`（末个 Chart.ChartType）→ 确定性研判 + 可选 AI 研判（走 RequireProfile+OpenAiCompatibleClient，无 key 回退确定性）。前端 `renderAdjudication` 把 JSON 拆成结构化 HTML，杜绝把原始 JSON 当正文渲染的乱码。

### 7.8 ChartTypeMapper 柱状图曾映射成 3D 饼图（v1.19.x）
- **根因**：`ResolveXlChartType` 中 `ColumnClustered` 误映射为 `-4102`（`xl3DPie`）。
- 正确映射：`xlColumnClustered=51`、`xlColumnStacked=52`、`xlBarClustered=57`、`xlBarStacked=58`、`xlLine=4`、`xlPie=5`、`xlArea=1`、`xlXYScatter=-4169`、`xl3DPie=-4102`。
- **改完必须真机回读 `Chart.ChartType` 核对实际值。**

### 7.9 内置流程模板缺 Arguments，缺参步骤逐个报「缺少必填参数」（v1.20.x）
- **现象**：`run_workflow` 内置流程如「透视汇总表」跑挂——步骤 2 `create_excel_pivot_summary` 报 `缺少必填参数：source_address`，修完又轮到步骤 3 `format_excel_range` 报 `缺少必填参数：address`。
- **根因**：`WorkflowStore` 内置模板所有步骤**完全没有 Arguments**，本意是依赖 AI 调用 `run_workflow` 时传 overrides 补参；AI 一旦漏传，第一个需要参数的步骤就抛 `Required(...)` 终止流程。
- **修复**（双层兜底）：
  1. 工具层宽容：`create_excel_pivot_summary` 的 `source_address` 缺省回退当前多格选区（`CurrentSelectionAddress`），`target_address` 缺省放源区下方 2 行，`label_column` 缺省 1，`value_column` 用 `DetectNumericColumn` 从右向左探测首个数值列（跳过表头）。
  2. 模板层接线：6 个透视类内置模板给数据步骤补 Arguments——源区域用 `{selection}`/`{selection_sheet}`（桥接层 `ExecuteWorkflowInternal` 对引用该占位的模板自动注入当前选区），透视产物供后续步骤用 `{stepN.target_address}`（`create_excel_pivot_summary` 输出含 `target_address`）。`export_excel_chart_image` 的 `file_path` 属用户输入，仍留给 AI 提供。
- **规避要点**：内置模板新增步骤时必须同时给 Arguments；占位符 `{selection}` 与 `{stepN.xxx}` 的解析分别在桥接层选区捕获与 `CaptureStepOutput`，两者缺一不生效。验证须真机跑完整流程（不仅单步）。

### 7.10 真机 harness 跨工具调用持有 ws/wb RCW 必被工具 FinalRelease 连带销毁（v1.20.x）
- **现象**：harness 在 Excel 工具调用前持有 `ws = wb.Worksheets.Item[1]`，工具执行后再读 `ws.Cells[...]` 抛 `COM 对象与其基础 RCW 分开`。
- **根因**：见 1.1——CLR 按 COM 对象标识缓存 RCW，工具 `FinalReleaseComObject` 销毁共享 RCW，harness 持有的同名 RCW 一并失效。
- **规避**：harness 一律无状态——读写经 `app.ActiveWorkbook` 重新解析、用完 `Release`，绝不跨工具调用持有 worksheet/workbook 引用。

### 7.11 PT 面板注入的 `sel_range` 是「带单引号表名 + 绝对地址」契约，模板严禁臆改格式（v2.0.0.0）
- **契约**：`index.html` 的「插入选区」把选区地址统一补成 `'工作表名'!$A$1:$B$6`（带单引号表名 + `$` 绝对引用 + 显式 `!`），注入为 `sel_range = "'Sheet1'!A1:B6"`。多选区则逗号连接（`'S1'!A1:B2,'S1'!D4:E6`）。
- **后果**：Python 预置模板（如 `py_chart_selection`）用 `sht.range(sel_range)` 时，xlwings 能正确解析带引号表名的地址，把数据源绑到指定表（即使图表画在活动表）。**若面板格式变（去引号/改 R1C1/换分隔），模板会静默画到错误区域或抛错**——这是前端与模板之间的隐式耦合。
- **规避**：① 模板访问注入用 `globals().get('sel_range') or '<演示址>'`（避免未注入时 NameError，缺省回退设固定演示区域）；② 改面板注入格式前必须同步核对模板；③ 真机 harness 的注入字符串要与 `index.html` 同一格式（本项目 VPC-1/4 用 `'Sheet1'!A1:B6` 已在源码核对下与前端一致）；④ 画图模板面向单一连续区域，多选区（逗号连接）为已知限制。
- **备注**：面板「插入选区」前会自动剥离旧的 `# XAI_SEL:` 标记行（去重），重复插入不会叠加。

### 7.12 参数框「假选项」防御：双向契约审计锁定 UI 字段 ↔ 工具 schema（v2.18.8）
- **现象**：用户反馈配置弹窗「选项有些不正确」——有的下拉没选项、有的选项工具根本不读（假选项）。
- **做法**：`RibbonCommandPlannerTests` 新增**双向契约审计**（18 工具全覆盖）：
  - 方向① `ConsumedUiFieldNames`：`BuildFields` 暴露的每个字段名必须被 `BuildArgs` 同名消费，否则是「死字段」。
  - 方向② `RealToolParameterContract`（真实 schema 参数名）：`BuildArgs` 产出的每个键必须落在 schema 参数内，否则是「假选项/未接线」。
- **三层闭环**：单测契约（方向①②）+ 渲染层 `VerifyParamJson`（真实 ParameterForm.html + 真实 BuildFields 进 WebView2，断言选项文本/Hint/默认值非空）+ 执行层 `VerifyParamOptions`（真机独立 Excel，断言新选项端到端生效）。任一假选项都逃不过这关。
- **坑点**：xUnit 无 `Assert.Contains(string, IEnumerable, string)` 重载，第三个参数被当比较器 → CS1503 编译错；改 `Assert.True(collection.Contains(x), msg)`。

### 7.13 转置跨表写回：`sheet.Range[address]` 不接受 `表名!地址`，须独立 `target_sheet` 参数（v2.18.8）
- **现象**：转置配置弹窗 `target_address` 提示用户可填 `Sheet2!C3` 跨表地址，但写路径 `sheet.Range[address]` 在目标表上解析含 `!` 的地址会失败/错位（与 5.9 xlwings 同源教训）。
- **修复**：新增 `target_sheet` 实参（工具 schema 本就支持），BuildArgs 把它映射为写出 sheet；`target_address` 提示改为「如 F1；跨表写入请另填目标工作表名，不要把表名写进地址」。
- **规律**：凡「写回位置」类选项，跨表一律拆成 sheet + address 两个独立参数，禁止把表名塞进地址。

### 7.14 弹窗默认值双路径分歧与数值边界（文档化，非缺陷）
- **text_clean collapse**：弹窗复选框默认勾选 `true`（清洗更符合直觉），工具 schema/AI 直调默认 `false`。弹窗路径总是显式传参（行为=勾选值），AI 路径缺省 false。改任一侧会牵动另一路径行为，**勿当 bug 乱改**；核对默认值一致性时按「弹窗显式传参=用户所见即所得」理解。
- **fill_random_numbers min>max**：工具在反转区间 [max, min] 内取值、不报错（无越界无 NaN）。BuildArgs 已校验数值格式并拦截 min>max（返回「最小值不能大于最大值」），并拦截 NaN/±Infinity（见 7.16），属弹窗路径防御。

### 7.15 Agent 操作：同一文件的多个 Edit 必须串行（2026-09-07，neat-freak 同步时踩；2026-09-08 源码编辑复现）
- **现象**：对同一文件并行提交 2 个 Edit（不同位置），两个都报"成功"且片段正确，实际落盘只剩后一个的改动，前一个静默丢失。2026-09-07 首次踩于 .md（AI交接文档标题回退）；**2026-09-08 复审在 .cs 源码上复现**（ExcelImportService 两处防线并行提交，copy_as_new_sheet 分支的 NO_MATCHED_SHEET 防线被静默冲掉，真机 m7 用例 ② 才抓到）。
- **根因**：并行写回基于同一旧快照，后写覆盖先写，无冲突提示。构建通过 ≠ 两处改动都在（少一处照样编译成功）。
- **规避**：① 同一文件的多次编辑一律**串行**提交（跨文件才可并行）；② 多处同型改动（如双分支同款防线）落盘后必须 `grep -c 关键字` 计数自检（本次预期 2 实得 1 即暴露）；③ 该类"静默成功"必须用真机/行为用例兜底，编译+单测都抓不到。

### 7.16 net48 double.TryParse 能解析 NaN/Infinity 符号，规划层必须显式拦截（v2.18.8，对抗审查第二轮）
- **现象**：`double.TryParse("NaN", NumberStyles.Float, ...)` 与 `"Infinity"/"-Infinity"` 在 .NET Framework 4.8 **均返回 true**（符号解析不受 NumberStyles 限制，.NET Core 3.0+ 才收紧）。min/max/step/start 填入 NaN/Infinity 后：`NaN > max` 恒 false 逃过大小校验 → NaN 渗透到工具层填格（Excel 显示 #NUM! 或写坏数据）。
- **验证**：Add-Type 实测 `P("NaN")=True`、`P("Infinity")=True`；`"1e999"` 溢出返回 false（无需额外处理）。
- **规避**：凡 `double.TryParse` 解析用户输入，一律追加 `|| double.IsNaN(x) || double.IsInfinity(x)`；已落地 fill_random_numbers（min/max）与 fill_number_sequence（step/start）。

### 7.17 互斥选项组合要在规划层拦截，不留给工具层"未定义行为"（v2.18.8）
- **现象**：transpose_range 选「原区域左上角」（写回源区）却填了「目标工作表名」——工具层无对应组合语义，行为未定义。
- **规避**：规划层对矛盾组合显式报错（「目标工作表名需配合『指定位置』模式使用」），并加单测锁定。凡「模式 A 的选项 + 模式 B 的选项」同时出现，规划层第一道防线拦截，勿依赖工具层兜底。

### 7.18 工具层无上限保护时，规划层按选区规模补预算上限（v2.18.8）
- **现象**：insert_blank_rows_every_n 工具层只 `Math.Max(1, ...)` 不设上限，interval=1、count=10 万会在选区每行后插 10 万行，远超 Excel 行上限。
- **规避**：规划层按 `(sel.Rows / interval + 1) * count` 预算插入总量，超 100000 拒绝并提示调小参数；单测覆盖超限/正常两路。

### 7.19 弹窗类 UI 路径无法自动化点击：判定抽纯函数 + 真机验证决策链路（v2.18.8）
- **现象**：Ribbon 守卫拦截（目标带数据）、执行后自检告警、随机样本锚点三条路径末端都是 `MessageBox.Show`，自动化 harness 无法点击弹窗，导致「服务层私有逻辑无单测 + 无真机覆盖」的双盲区。
- **规避**：把弹窗**之前的决策逻辑**抽为纯函数入 `RibbonCommandPlanner`——`MatrixHasData`（0 基矩阵占用判定）、`PickSampleValues`（样本提取），服务层 `BlockHasData`/`VerifyRandom` 委托之；单测锁定边界，harness 用例 20 用真实 COM 数据端到端验证决策链路（空区放行/有数据拦截/值域自检/越界被抓）。弹窗文案本身仍属人工验证项，但决策正确性已自动化闭环。
- **教训**：写"弹窗"功能时先问自己「弹窗前那段判定能不能抽出来测」——能抽则抽，避免把可测逻辑焊死在 UI 线程上。

### 7.20 覆盖写工具丢弃 writer 的 operation_id/AffectedRanges → 操作不可回滚（v2.18.8）
- **现象**：sort_range / dedup_range / find_replace_range / transpose_range 经 `writer`(WriteGenericRange) 落盘后，返回结果直接 `new ToolResult { Data = new { ...工具统计 } }`，把 writer 产出的 `operation_id` 与 `AffectedRanges` 整体丢弃。前端拿不到 operation_id 就无法调 `undo_excel_operation`，覆盖写操作**不可回滚**——自检/回滚链路的隐含契约是「写操作结果必须带 operation_id」。
- **规避**：新增 `MergeToolResult(writerResult, data)` 统一合并——保留 writer 的 `operation_id`/`AffectedRanges`/`written_cells`/`shape_refit`，再并入工具统计字段；四个工具返回点全部改走它。失败路径特判：writer 失败时其 Data 是错误文本（string），直接原样返回，**禁止对 string 反射 `GetProperties`**（会命中索引器属性 `Chars`，无索引参数 `GetValue` 抛 `TargetParameterCountException` 掩盖真实错误）。其余合并反射统一过滤 `GetIndexParameters().Length == 0`。
- **验证**：单测 `ExcelDataToolsServiceTests` 用 fake COM + fake writer 锁死四个工具的 operation_id/AffectedRanges 透传与失败路径不崩溃；真机 harness 新增用例 21（排序 → 取 operation_id → undo → 矩阵比对恢复原状）。默认值审计自动化：`ParamDefaultsAuditTests` 从「参数框默认值 → BuildArgs 实参 → 工具缺省 fallback」三端锁死 sort_range / dedup_range / transpose_range 的默认值一致性，防止参数框默认值改动后与 AI 直接调用路径行为分歧。
- **教训**：凡是"经统一 writer 回调落盘"的工具，返回结果必须透传 writer 的撤销标识与影响区域，切勿只回组装统计字段——写操作结果契约 = `operation_id` + `AffectedRanges` + 工具统计。

### 7.21 M6 复审（2026-09-08）：同型缺陷按"调用点"排查，一处修复≠一族修复
- **背景**：M6 修复了 `ArgsStringArray`/`ArgsNameArray` 不识别 schema 对象项的契约缺陷，但只修了 `merge_delimited_files` 等直接调用点——**同文件内 `import_excel_file_sheet` 的 `sheets` 参数（schema 声明 `{name}` 对象项）仍走旧硬编码 `path` 键解析**，按 schema 传参解析出类名字符串 → 0 表命中静默 OK。M6 full 真机当时给 OK，因 harness 传的是纯字符串数组而非 schema 对象项——**"真机 OK"只覆盖 harness 实际传参形态，不覆盖 schema 声明的全部合法形态**。
- **修复**（双副本同步，`ExcelImportService`/`ExcelWorkbookService`/`SidebarBridge`）：
  1. `ArgsStringArray` 增加 `itemKey` 参数（sheets→name、file_paths→path），对象项缺声明键一律跳过（禁止类名字符串混入）；`ExtractItemString` 同规则。
  2. 静默成功防线：`merge_workbooks` 全部路径无效 → `NO_VALID_SOURCE`；`import_excel_file_sheet` 指定 sheets 0 命中（两分支）→ `NO_MATCHED_SHEET`——"处理 0 项"不得返回 OK。
  3. `SidebarBridge` WPS 无 VBA 提示词与实际工具清单矛盾（声称 save_vba_tool 不可用，实际 CreateRegistry 无条件保留）——口径对齐：save_vba_tool 在清单中但仅写库文件，模板执行不可用。
- **验证**：harness 新增 `m7` 模式（exclusive 守卫同 battery）三用例真机全过：①`{name}` 对象项导入 OK（imported_sheets 命中）；②不存在表名 → `NO_MATCHED_SHEET`；③全无效路径 → `NO_VALID_SOURCE`。双副本 872/872 单测回归通过。
- **规律**：修"参数解析族"缺陷时，先 `grep` 该解析函数的**全部调用点**逐一核对 schema 声明的键名；新增解析能力时同步补"空结果显式报错"防线；AI 可见提示词中"某工具不可用"的表述必须与 CreateRegistry 的实际注册行为对齐（save_vba_tool 是特例——注册但执行体不可用）。

### 7.22 M10（2026-09-08）：sln 构建（AnyCPU）不产平台输出，CS0165 只在显式平台构建暴露
- **现象**：`dotnet build ExcelAiAssistant.sln -c Release` 0 警告 0 错误 + 872/872 单测全绿，但 `bin/x64/Release/.../win-x64/ExcelAiAssistant.Addin.dll` 仍是旧代码——sln 默认平台（AnyCPU）不会编译 `-p:Platform=x64|x86` 的平台输出目录。按旧 DLL 打包 → 新方法（GetWpsEnvironment）缺失，且字节级检查才暴露。
- **同一构建的真错误**：显式平台构建才暴露 CS0165（vbaEvidence 条件赋值路径编译器无法证明必赋值）——"sln 全绿"对平台产物是假阴性。
- **规避**：改 Addin 侧代码后，交付打包前必须跑 `dotnet build ...Addin.csproj -c Release -p:Platform=x64` 与 `x86` 各一遍并核对产物 mtime；对安装落位的 DLL 做**字节级关键符号检查**（如 `grep` 方法名字节串）验证版本一致性，不信任文件时间戳（Inno 会保留源 mtime）。
- **关联坑**：Inno 安装后文件时间戳 = 源编译时间 ≠ 安装时间，用"落位文件 mtime"判断"是否装上新版"必然误判。

### 7.23 侧边栏 JS 时序死区（TDZ）：先引用后声明的 `const` → 检测按钮 100% 报错（v3.0.0.0 WPS 环境卡）
- **现象**：设置页「WPS 环境·指南」点「检测本机 WPS 环境」必报 `检测失败：Cannot access 'r' before initialization`，用户截图实锤。字段全部停在"—"。
- **根因**：`refreshWpsEnvironment()` 内 `r.host_kind` 的使用行写在了 `const r = parseResult(await asyncBridge.GetWpsEnvironment())` **声明之前**——JS 的 let/const 时序死区（TDZ）是运行时错误，`node --check` 与括号配平审计（SidebarInlineScriptAuditor）**都抓不到**（语法合法）。
- **规避**：①桥接结果 `const r = parseResult(...)` 必须是函数体 try 块的**第一行**，任何 `r.*` 引用不得上移；②新增 UI 行为改动除静态审计外，用 Node `new Function` 桩环境（stub elements/asyncBridge/parseResult）**真跑一遍**渲染函数断言字段值——TDZ/引用错误只有运行时才暴露；③错误文案是"检测失败：<原始 JS 报错>"直出，若见 "before initialization" 字样即 TDZ 特征，直查声明顺序。
- **验证证据**：修复后桩环境三用例（WPS 个人版载荷 / 桥接抛异常 / Excel 宿主+未注册）全过；`node --check` 1 个 script 块 OK；872/872 单测含 JS 静态审计全绿。

## 8. 数据 / 选区 / 公式语义

### 8.1 Excel Value2 写 ISO 日期字符串会自动转数值(OADate)
- **现象**：回读时该列数值占多 → `ColumnKind` 判 numeric 而非 date → 坏日期(format)检测分支永不触发。
- **修复**：先 `range.NumberFormat="@"` 把该列设为文本再写入，使日期串保持文本形态。

### 8.2 flag_cells 建诊断表后 ActiveSheet 被切换
- `CreateDiagnosisSheet` 用 `Worksheets.Add()` 会令 ActiveSheet 变为新诊断表。真机 harness 跨表断言不得依赖 `app.ActiveSheet`，须显式 `Workbooks[...].Worksheets["dt"]` 定位。

### 8.3 flag_cells 空值检测含全空列
- 种子只填 N 行却声明 A1:BN(N+1)，第 N+1 整空行会被 empty 检测计为多个空值。断言前须精确填满目标区域、不留多余空行。

### 8.4 公式解释多格选区规则
- 无公式格返回 `has_formula:false`；选区公式格 >20 时仅解释激活格并提示「选区公式过多，仅解释激活格」；主格取选区首有效公式格。

### 8.5 公式引用解析要求
- `pos` 必须带工作表名；跨表/跨簿引用需读取公式，不得降级为「无法读取」；`ExtractCellRefs` 需覆盖 `$A$1`、`C:C`、`'带空格表'!B2`、`[Book]Sheet!A1` 等变体；R1C1 样式标记为 `UNPARSED:` 哨兵。

### 8.6 智能填充参考上下文
- 采用「整行邻近上下文（同行各列值）+ 同列分布」双料；数值空格无语义依据时填 `"待补"`；默认 `reference_scope=same_sheet`，`whole_workbook` 需显式请求并提供来源。

### 8.7 选区处理约束
- 按钮侧需检测选区是否为单块矩形，非矩形直接弹「请选择矩形区域」；处理空格超过 5000 个需显式提示「仅处理前 5000 空格，其余忽略」。

### 8.8 循环引用检测
- 环键按工作表隔离；visited 集合检测到重复地址立即判环（环优先于深度）；间接环（如 `X1=Y1, Y1=X1`）需手工预验证落盘可行性。原实现仅直接命中 visited 时判环，导致 2 跳间接环被遗漏（`BuildLinked` 需补间接环检测）。`ParseFills` 需补齐对普通 Dictionary 输入兼容。

### 8.9 merge_sheets 表头合并规则
- include_headers 时，首个源表取 matrix[0] 作合并表头，其余源表假定共享同一表头，一律跳过首行（dataStart>=1）。

### 8.10 技能包 zip-slip 漏洞防护
- 导入技能包必须手动逐条解压并校验（`ExtractSkillPack`），检查条目路径是否含 `../` 或绝对路径，确保目标路径在安全范围内，越界即抛异常。

### 8.11 COM Value2 写入重解析：长数字/前导零字符串必须先锁文本（v3.8.1.76）
- **现象**：真机自检实证 AI 用 write_excel_range 写 18 位身份证被 Excel 按"手工输入"语义重解析为 5.787E+17（double 精度丢失，数据损坏级），"007"→7 前导零丢失，日期串→日期序列号；写入报 ok 但回读值与预期不符。
- **修复**：WriteRangeCore 写入前经 Core `TextPreserveAdvisor` 判定（纯数字 ≥11 位或前导零纯数字）逐格预设 `NumberFormat="@"` 再整块写值；`text_locked_cells` 回显锁格数。日期串不拦（原生日期化与手工输入一致），但写入后回读比对，长字符串（≥8 字符）被存为数值/日期时经 `coerced_cells`/`coerced_count` 上报给 AI 复核——把静默漂移变成显式信息。锁格失败不阻断写入（AppLog.Warn 留痕后原样写）。
- **教训**：COM 写入的字符串不是"写什么是什么"，Excel 会重解析；任何"文本语义"的长数字必须前置锁格式，且必须在返回值里让 AI 看见重解析。

### 8.12 WPS 宿主 FormatCondition 的 dynamic 分派可能丢 Interior/Font 成员（v3.8.1.76）
- **现象**：真机自检报 `verify_conditional_format ok=False VERIFY_CONDITIONAL_FORMAT_FAILED："System.__ComObject"未包含"Interior"的定义`——同一规则类型/公式读取正常，唯 Interior/Font 属性 dynamic 分派抛 RuntimeBinderException（踩坑 §2.1/2.2 dynamic 丢运行时成员同族），且原实现一票否决整个自检。
- **修复**：`VerifyConditionalFormat` 对 `fc.Interior`/`fc.Font` 两处读取单独 try-catch 降级（读不到即 null），颜色断言同步跳过（expected 置空防"读不到"误判为"颜色不符"），issues 明示"请人工目视核对颜色"、`color_check_skipped=true` 回显、AppLog.Warn 留痕；规则类型/公式/运算符校验照常执行。
- **教训**：跨宿主（Excel/WPS）COM 面的 dynamic 成员读取一律不得裸奔——子对象属性访问单独容错并降级披露，不能让装饰性字段（颜色）的读取失败拖垮核心断言（规则类型/公式）。

## 9. 开发工作流与文档维护

### 9.1 同一条消息并行编辑同一文件 → 写竞争吞掉前序改动（v2.18.9 发版同步踩坑）
- **现象**：批量同步多份文档版本号/断言数时，一次消息内连续发多条 `Edit` 改**同一个 .md**，部分修改未持久化——Edit 返回快照里短暂可见、最终文件只留下最后一次写入。本次 CLAUDE.md 版本行、AI交接文档前 3 处编辑均被吞，仅靠末次写入幸存。
- **根因**：对同一路径的多条同批 `Edit` 做读→改→写竞争（last-writer-wins），非预期的并发写盘互相覆盖。该目录已确认**非 git 仓库、非 OneDrive/符号链接**（`git status` 报 not a git repository，Attribute=Archive，无 LinkType），排除外部还原，纯属工具链同批写竞争。
- **规避**：对**同一文件**的多次编辑**必须串行**——一次只发一条 `Edit`（多条 `Edit` 可分发给不同文件才安全）；每发一条即用 `rg`/`Read` 核验落盘，再发下一条。发版"多文档版本号同步"这类高密度改动尤其要逐条改、逐条验。
- **文档纪律（本项目强制）**：编辑含真实版本/断言数的文档（CLAUDE.md / AI交接文档 / readme）时，同步完必须做一次全文 `rg` 残留核验（搜旧版本号/旧断言数/旧单测数），确认零残留再收束——本次正是靠终检揪出被吞的 CLAUDE.md 版本行。
- **相关**：见 §6.6 坑3（PS5.1 读无 BOM 的 .ps1 中文字面量乱码导致 Test-Path 恒 False）——两坑都要求"写入/完成即回读核验"，勿信任写操作返回的快照。

### 9.2 构建/打包时 bin 的 Addin.dll 被运行中的 Excel 锁定 → MSB3027（v2.19.3.0）
- **现象**：`dotnet build Addin -p:Platform=x64` 报 `error MSB3027/MSB3026：无法将 obj 的 Addin.dll 复制到 bin…文件被 "Microsoft Excel (PID)" 锁定`，重试满 10 次失败。x86 却正常（未加载架构）。
- **根因**：用户在带加载项的 Excel 里打开工作簿（`MainWindowTitle` 非空 = 有可见窗口、活动会话），DLL 被进程加载锁定，MSBuild 覆盖 bin 失败。**不是代码错误**——obj 已编译成功，仅拷 bin 被挡。
- **规避**：先让用户**保存并关闭**加载了加载项的 Excel（勿强杀进程，避免丢未保存数据），再构建/打包。判定它是否"用户会话"：`Get-CimInstance Win32_Process` 看 CommandLine 是否带 .xlsx/.xlsm 参数 + `Get-Process EXCEL` 的 MainWindowTitle 非空；无工作簿参数/无窗口的通常是残留 harness 实例，可安全结束（harness 会自动按 PID 清理）。
- **验证**：Addin/前端改动后 x64/x86 各构建一次通过 + 打包 ReleaseGate 会再次兜底。

### 9.2a Addin 工程限定 x86;x64 平台（无 AnyCPU），外部工程 ProjectReference 会连环失败（v3.8.1.77 AI Skill 批次实证）
- **现象**：为验证 `SkillPackInstaller.InstallSkillFromRepo`（internal）做外部真机闭环——①独立 net48 反射 harness：`dotnet run` 启动即崩（exit 127「Exception.ToString() 失败」，异常类型自身无法加载）；②Tests 工程 ProjectReference Addin：CS0234/CS0246「命名空间不存在」——均因 Addin csproj 声明 `<Platforms>x86;x64</Platforms>`（无 AnyCPU）+ RuntimeIdentifier 条件（win-x86/win-x64），Tests（AnyCPU）的引用解析报 NETSDK1047（assets 无 net48/win-x64 目标）；SetPlatform=Platform=x64 仍触发 restore 侧 RID 缺口。
- **后果链**：继续修复需给 Addin 配双 RID restore 或改 Platforms——两者都动了发版关键工程（pack 按 x64/x86 显式平台构建），风险大于收益。
- **处置**：回退 Tests 引用/InternalsVisibleTo/harness，闭环验证改走「用户重启产品实测」通道（含精确测试步骤交付），常驻回归锁由 Core 纯逻辑单测承担（解析/标记/三档/注入 29 例）。
- **教训**：平台受限工程（无 AnyCPU + 条件 RID）的 internal 代码做自动化真机验证，正确路径是产品内探针（XaiProbe 模式）或用户实测，不要让测试需求反向改发版关键工程的平台/restore 状态；`InternalsVisibleTo` 单独加上无害但无引用通道时无效。

### 9.2b 宿主内 WebClient 直连 GitHub 被 TLS 掐断 → jsDelivr 镜像兜底（v3.8.1.79 实证）
- **现象**：真机点「在线安装」报「请求被中止： 未能创建 SSL/TLS 安全通道」——net48 加载项运行在 Excel 宿主默认 AppDomain，`ServicePointManager.SecurityProtocol` 默认协议栈与 codeload.github.com 握手失败。
- **修法**：①`EnsureModernTls` 显式 `|= Tls12|Tls13`（只升不降，URL 与仓库两安装通道统一接入）；②codeload 失败自动切 jsDelivr 两段式（`SkillMirrorPlan`：data.jsdelivr.com flat 清单定位技能目录 → cdn.jsdelivr.net/gh 按文件下载重建目录，main/master 双分支，直连与镜像全败才报错且注明已尝试通道）。
- **关键坑**：jsDelivr flat 清单条目**无 type 字段**（1251 条实证）——计划器不得要求 `type=="file"`，仅显式 `"directory"` 才跳过；深层技能目录按 `name.IndexOf("/"+skillDir+"/SKILL.md")` 匹配（net48 无 Contains 双参重载）。

### 9.2c 受保护 EXCEL.EXE 僵尸进程阻塞静默安装（v3.8.1.80 实证）
- **现象**：`Setup.exe /SILENT` 长时间无结果且落位版本不变；进程列表见安装器驻留等待。机器上有一个 EXCEL.EXE（无命令行、56K 内存、非 gate 拉起——gate 双泄漏刚通过），`Stop-Process -Force` 报 **Access denied**（受保护/提权实例），session 内杀不掉。
- **处置**：安装器追加 `/FORCECLOSEAPPLICATIONS`——Inno Setup 经 Windows 重启管理器强制关闭占用应用，静默安装立即成功（60s 内落位）。
- **教训**：静默安装「无结果」先分层核实：①落位版本戳（判断是否执行）；②`tasklist` 查安装器是否驻留等待；③查宿主占用进程（EXCEL/WPS）——对杀不掉的受保护进程不要反复 taskkill 硬试，直接上 `/FORCECLOSEAPPLICATIONS`；另外先清掉上次超时遗留的安装器进程再重试，避免双实例互相等锁。

### 9.2d 受保护僵尸 EXCEL.EXE 连 FORCECLOSEAPPLICATIONS 都压不住 → 只能交用户（v3.8.1.82/83 连续两批实证）
- **现象**：EXECL.EXE 无命令行+低内存（受保护僵尸分型），`/FORCECLOSEAPPLICATIONS` 加了静默安装仍挂起；与 9.2c 的可解形态（重启管理器能关）不同，此形态两次尝试均无果。
- **处置**：两次尝试后按纪律停试，不盲试第三轮——清理挂起安装器进程，安装包交用户手动双击（或重启清僵尸后再静默装）。
- **教训**：安装阻塞三分型处置链（9.2c 沉淀）走完仍失败即止损，机器重启是唯一可靠清理手段；不要在同一挂起形态上消耗轮次。

### 9.2e net48 编码三连坑：Contains 双参重载缺失 / JSON key 大小写 / 成员遮蔽命名空间（v3.8.1.83 联网搜索批次实证）
- **net48 `string.Contains` 无 `StringComparison` 双参重载**（CS1501）——大小写不敏感匹配一律 `IndexOf(x, StringComparison.OrdinalIgnoreCase) >= 0`。
- **JArray/JObject 匿名对象序列化**：`results` 若直接投影类属性（PascalCase 如 `Title`），序列化后 JSON key 大写，下游/真机测试按小写 `title` 断言即失败——投影时显式用小写字段匿名对象。
- **同名成员遮蔽命名空间**：类自身有名为 `Search` 的方法成员时，代码里裸写 `Search.xxx` 解析到成员而非 `Search` 命名空间（CS0103 或错误绑定）——跨命名空间调用写全类名（如 `SearchProviderDetector.Detect`）。
- 另：大段工具文件多轮 edit 有拼接损坏风险（Execute 方法重复块），损坏后局部 edit 越修越乱——读回受影响区域整块重写更可靠。

### 9.2g 批量源码插桩事故与恢复方法学（2026-09-17，日志批次实录，v3.8.1.85）

**事故**：正则插桩脚本 patch_logs_v3.py 三缺陷系统性损伤三工程源码（峰值 2400+ 编译错），且无 git 无备份。

**三缺陷（脚本设计红线）**：
1. 多行 catch 块重建时丢弃闭合 `}`（每站点恰丢一个）；
2. 单行 `try{..}catch{..}` 的 `{` 被误当 catch 块起点，日志插进 try 体引用未声明变量（CS0103）；
3. brace 配对计数被字符串字面量/注释内花括号欺骗。

**恢复方法学（工具闭环验证）**：
1. **NEW-only 甄别**：先算损伤文件相对备份底稿的独有行数。=0 → 整体取备份零损失；>0 → 独有行是真实增量必须保留，逐段手术；
2. **降序 graft**：多段替换必须按行号降序应用——升序时前面段膨胀会把后面所有段行号推偏（曾致 139→219 错误反弹）；
3. **深度走线定位**：`_dev_tmp/probe.py`（catch 站点扫描）、`probe2.py`（方法级深度）、`trace_depth.py`（行级走线）、`chunk_depth.py`（分块走线）四级定位失衡区间；
4. **先备份后动刀**：任何批量脚本跑之前先全量快照（本批 `_backup/src_snapshot_20260916_prelog/`）。

**插桩重写（v4）设计红线**：
1. 只做**行内插入**（在 catch 开括号后插一行），绝不重建 catch 块；
2. 括号计数前剥离字符串/字符字面量/行注释；
3. 插入前后 depth 剖面逐行断言一致，不一致立即回滚整文件；
4. 单行 catch 一律跳过（零结构风险优先）；
5. 残骸扫描兜底：插桩后全库扫孤立 `$"` 插值行与缺 `Write(` 前缀行；
6. **自引用打点禁令**：日志基础设施自身（DiagnosticsLog.Append）的 catch 不得打日志——Write→Append→失败→Write 会无限递归，靠内存环缓存天然留痕即可；
7. 返回值字段增删须 grep 全库 dynamic 引用（analyze_column_correlation 删 `strong` 字段曾致 WPS full 真机 dynamic 反射 FAIL）。

### 9.2h 公式构造器三 bug + PowerShell 针词检索误报（2026-09-18 公式闭环批次实证）

1. **RangeRef 尾端点重复工作表限定是非法形态**：`'S'!$B$2:'S'!$B$5` 不被 Excel 接受——工作表限定只放首端点（`'S'!$B$2:$B$5`）。
2. **带引号工作表地址解析正则**：`'Sheet'!` 的 `!` 必须划入引号分支（`'(?:[^']+)'!`），漏 `!` 会让带引号形态整体解析失败。
3. **criteria 单元格引用识别**：`$H$1` 形态正则须允许首列 `$` 前缀（`^\$?[A-Za-z]{1,3}\$?\d+$`），否则被误判文本加引号。
4. **cell.Text 判错误值有假阳性**：窄列数字显示为 `####`（同以 # 开头），Text 是显示串——错误值检测须用 Value 类型（COM 返回 Int32 2000~2042=XlCVErr：2000=NULL!/2007=DIV0!/2015=VALUE!/2023=REF!/2029=NAME?/2036=NUM!/2042=N/A）。
5. **构造器必须校验列序与表头行边界**：value/criteria/weight 列序超源区域宽度会生成引用源外区域的错公式；表头行数≥总行数时数据区为空——均应 fail-closed 拒绝。
6. **criteria 跨表单元格引用直传**：`参数表!$B$1` 形态须在文本加引号之前识别（正则含中文工作表名）。
4bis. **PowerShell UTF-16 针词检索误报（9.2 系再实证）**：`Encoding.Unicode.GetString` + `Contains` 对装配体检不可靠——同一 DLL 四个字符串两真两假。**装机/入包体检以 python 字节级核对为准**（`name.encode('utf-16-le') in bytes`）。
5. 另：C# 方法返回值上不能直接跟对象初始化器（`O(...) { X = 1 }` 非法，CS1002）——测试助手改 With(o => {...}) 链式；元组析构 dynamic 返回值报 CS8133——改显式 Tuple。
### 9.2i 公式板块审查批次双真 bug + 发版链三坑（2026-09-19 公式板块审查批次实证）
1. **ToAbsolute/ToRelative 不得触碰字符串字面量**：`IF(A1="B2",..)` 里文本 `"B2"` 曾被篡改成 `"$B$2"`（正则把字面量当引用）——按 `"` 切分只对偶数段（字面量外）做替换（TransformOutsideStrings）；公式内文本相似引用是高频形态（编码/单号）。
2. **FormulaDiff 空白归一化必须字面量感知**：字符串字面量内的空格是内容差异（`"华东 区"` vs `"华东区"`），无差别 `\s+` 折叠会误判「未变化」——逐字符按 `"` 开关跳过字面量内空白。
3. **MatchEvaluator 与 Func<Match,string> 不互通**（CS1503）：`Regex.Replace(string, Regex 模式, MatchEvaluator)` 重载要求委托类型精确匹配，lambda 须显式声明为 MatchEvaluator 或改 Func 后用 `new MatchEvaluator(f)`。
4. **bump 会把历史叙事里的旧版本号全部改成当前版本**（已知系统性问题再实证）：交接文档/AI 行为准则里历史批次的「bump 3.8.1.9x」字样随发版漂移失真——读历史批次真实版本以 `Directory.Build.props` 变更记录与 pack stamp 断言日志为准，勿信文档内嵌版本号。
5. **HTML 内联 JS 校验脚本**：`re.findall(r"<script>(.*?)</script>", html, re.S)` 提取后拼接写临时文件再 `node --check`；多 script 块须拼接（1 块也统一走该链），别用正则裸验 JS。
6. **装机体检针词分载体**：Addin.dll 针词（中文 UI 字符串/桥接方法名）用 UTF-16 检索字面量 + UTF-8 检索标识符双口径；Core.dll 的纯逻辑类名（如 TransformOutsideStrings）用 UTF-8。

### 9.2j 0 行矩阵写入链数据破坏 + wpsufd 阻塞安装（2026-09-19 工具分类审查批次实证）
1. **ExcelRangeHelper.Resize 0 行钳行是数据破坏级真 bug**：`Math.Max(rows-1, 0)` 把 0 行/0 列钳成 1 行/1 列地址——FilterData 0 匹配/CleanData 全空行产生的 0 行矩阵写入该地址时，WriteRangeCore 的 Refit「值少则清空」语义会**清空源区域首行**。修复：Resize 对 rows<1||columns<1 fail-closed 返 null；FilterData/CleanData 对 0 行输出提前拦截返人话结果不写工作簿。凡「0 行输出」的变换类工具（筛选/去空行/切分）都须检查这条链。

3. **wpsufd.exe（WPS 更新守护）可阻塞静默安装**：3.8.1.98 两次静默安装超时（600s/1200s），现场驻留 wpsufd.exe 229MB——与既往探针遗留 EXCEL.EXE 阻塞不同型（wpsufd 是常驻守护非僵尸），未强杀，按纪律停试交用户手动安装。后续安装遇超时可先查 wpsufd 是否活跃。

#### 二轮审查补充（M-D1 收口，2026-09-10）

- **渲染失败必须回滚新建对象**：CreateKpiBrief 类"删旧+建新"长链路，catch 只处理特定异常类型时，其余异常会带着半成品逃逸（违反 AC-5）。通用 Exception 也要接住并清理本次新建的 sheet；错误文案里"已回滚"必须与实际行为一致，否则是假承诺。

### 9.x.2 M-D3 set_linkage 补充坑（2026-09-10，真机实证）

- **跨工具链式调用禁止依赖 ActiveSheet**：set_linkage 曾用 ActiveSheet 解析源数据表，而 render_dashboard 的 `Worksheets.Add` 会激活新表 → 联动挂错表（实测把 KPI 总额 2041627 当成了筛选字段名）。修法：源数据表显式 `sheet` 参数，schema 描述同步注明。
- **探针侧禁止用 `Worksheets.Item[1]` 定位明细表**：`Worksheets.Add`（无参）在活动表**之前**插入新表，渲染后表序为 [staging, 看板, 明细]，`Item[1]` 拿到 staging。正确做法：写种子数据前先记录明细表名，跨调用用记录值。
- **native 联动必须闭环改写 staging 公式**：只建切片器不改编公式 → 切片器驱动了隐藏透视表但 KPI/图表数值纹丝不动（T14b 曾 2041627→2041627）。修法：把 staging 公式从「SUMIFS 引 B2 控制单元格」改写为「SUMPRODUCT(SUMIF/COUNTIF 引透视标签区)」；透视「总计」行标签无明细匹配 SUMIF 贡献 0，语义自洽无需排除。切片器选华东 KPI=674323 与 cell 模式同值互证。
- **SUMPRODUCT+MATCH 数组式比 SUMIFS 慢约 4 倍**：native 改写后筛选重算实测 1060ms（cell 模式 249~497ms），略超 NFR-2 的 1s；优化候选=GETPIVOTDATA 直取。这是 native 联动方案已知代价，记录为观测项。
- **长方法写入必须一次成型**：复杂数组公式改写逻辑分两次写入时曾产生草稿级断裂代码（引用了未定义变量、注释残片），靠整体读回+整体重写修复；教训=写入前先把公式模板想完整，避免「先写壳后补芯」。
- **schema 与实现对齐纪律**：M3ToolSchemas 声明的可选参数（如 dim_cross 的 `sheet`）若实现未读取，工具会静默用 ActiveSheet 并挂错数据源（T16b 曾全量矩阵为 0，去重出 row=1/col=7 杂项维度）；新工具交付前必须逐参数核对「schema 声明 = 实现读取」。
- **探针新增用例插入位置敏感**：向长探针段插入用例时，锚点（如 `board.Range["B2"].Value2 = "全部"`）在文件中多处出现会把用例插到中段破坏后续用例的表状态假设（曾致 CS0128 重复定义 + 用例顺序错乱）；插入后必须 grep 确认只出现一次，且放在会改变活动表/新增 sheet 的用例之后。
- **verify_dashboard 判别 KPI 须双重感知（公式 + 函数括号）**：辅助区扫描若盲取 A 列值，dim_cross 布局（A1=控制单元格文本）会误报 mismatch；一轮修复只感知「公式存在性」仍亮红——dim_cross 的 A1 是纯引用公式（`=看板!$B$3`，镜像控制单元格，值恒为文本）。最终判别式：**有公式且含 "("（函数调用）才算 KPI**，纯引用公式跳过不计。审查断言（T17/T18）必须真机跑过才算修复，单测对该域零防线（变异测试实证：去公式感知注入后 986 全绿）。
- **审查断言用例必须紧跟被修复行为**：T17 的断言目标是「修复后 verify 不误报」，但首轮修复仅凭代码推理未覆盖「纯引用公式也是文本值」分支——靠真机一轮 FAIL 才暴露。教训：审查修复（尤其判别式类）写完先自问「输出数据形态还有什么会绕过判别式」，能枚举的分支直接进断言。

### 9.x.3 看板二轮审查（M-D3 优化轮，2026-09-10）

- **错误路径校验必须前置于资源创建**：CreateComboChart 曾先 `ChartObjects().Add` 再校验系列数/序号，两条错误路径残留空图表半成品（违反 AC-5 同源语义）。修法：错误 return 前调 `TryDeleteChartObject` 清理并置 null 引用。同类：直方图回退路径无数值行曾静默 return 残留空图表，改为返回 bool + 显式 NO_NUMERIC_DATA 拒绝。
- **图表 Points 对齐禁用源行号映射**：混入非数值行的源数据，Excel 图表 Points 点序与源行号不可靠映射（行号-1 曾实测 0x80070057 参数无效）。正确做法：读 `series.Values`（图内实际绘制值数组）按点索引对齐，与 Points 一一对应，语义最稳。
- **COM variant 数组是 1 基下界**：`series.Values` 返回的 Array 下界为 1（非 0），0 基 `GetValue(i)` 遍历曾致「索引超出了数组界限」全挂（T13/T20 同报错）。遍历一律 `GetLowerBound/GetUpperBound`。
- **staging 批量写公式须切手动重算**：Excel 默认自动重算下，每写一条 SUMIFS 触发全簿重算（2 万行实测 14.66s 超标）。修法：BeginBulkFormulaWrite（关 ScreenUpdating + Calculation=xlCalculationManual）→ 写完 EndBulkFormulaWrite（恢复 + 一次 Calculate）——生成耗时降至 9.27s 达标（-37%）。守卫必须在 finally 恢复，防异常路径遗留手动重算态。
- **edit_file 相同锚点多处出现会插错方法**：`sheetStaging.Name = "_" + ... + "_calc"` 在两个渲染方法中都存在，守卫赋值曾插进 dim_cross 而非目标方法（CS0103）；插入后必须 grep 变量名确认作用域与方法归属。
- **NFR-2 最终基线（Excel 16.0 out-of-proc）**：2 万行生成 9.27s（≤10s 达标）、筛选重算 322ms（≤1s）；2000 行生成 1.4~9.6s。PRD 已回填 v0.4。
- **TOOL_COUNT 卡点须剔除 ct_ 动态注册**：WPS full 巡检的沉淀样例用例（ct_hf_review_tool/ct_proc_* 等）会动态写入用户工具库并计入 TOOL_COUNT，导致该计数随用户库浮动（147→148 曾误判为代码变更）。对账口径改为「剔除 ct_ 前缀后的代码注册数」（EXPECTED=139=147-上轮遗留 8 个 ct）。教训：卡点计数若混入运行时可变集合，会在真实变更时变成狼来了。
- **KPI 卡公式禁自引用看板 sheet**：sales_overview 的 KPI 卡曾写 `=IFERROR('看板'!$A$1,…)`（引看板自身 A 列而非隐藏辅助表），A 列无值 → IFERROR 恒回退占位符，**看板 KPI 卡实际从未显示过数值**——此前探针断言只读 staging A1 未覆盖「看板显示值」而漏检。由 delete_dashboard 回读断言（找引用 _calc 的公式）反向揪出。修法：KPI 卡公式引用 `_calc` 表（与 kpi_brief 对齐）。教训：验收断言要断「用户看到的东西」，不是中间存储。
- **批量手动重算守卫有规模适用边界**：out-of-proc 下 Calculation 模式切换（ScreenUpdating/Calculation 读写 ×4 次 COM 往返 + 模式切换本身）有固定开销——2000 行（公式少）时 6.5s→10.4s **反而更慢**，2 万行时 14.7s→9.3s 快 37%。正确姿势=**行数阈值触发**（本实现 ≥5000 行启用），小表走原生增量重算。对照实验方法：注释开关 → 各跑一轮 → 数据定去留，不猜。
- **全簿 Calculate 换 sheet 级无收益实证**：EndBulkFormulaWrite 改 `Worksheets[name].Calculate()` 后 2 万行 11368→11381ms（噪声级）——瓶颈不在重算扫描而在渲染元素与 COM 往返本身；优化前先分段计时定位，勿按直觉优化。

### 9.x.11 诊断/修复闭环批次三坑（v3.7.1.37，2026-09-12）

- **服务 finally 释放共享 workbook/sheet RCW 是 repair/组合调用链的隐形炸弹**：VerifyChart 与 CreateChartAdvanced 的 finally 一直在 `Release(sheet/workbook)`——单工具调用无感，但 repair_chart（Verify→删旧→重建→复检）链路上，前置 Verify 的 finally 断开共享 RCW 后，后续 `sheet.Activate()` 即炸 InvalidComObjectException。全库纪律：**服务工具 finally 只释放方法内新建的局部 COM 对象**（range/collection/chart），workbook/sheet 交给 GC。
- **Excel Resiliency（崩溃禁用标记）= "功能区选项卡消失"的头号根因**：Excel 崩溃/强退后把 COM 加载项记入 HKCU\...\Excel\Resiliency\DisabledItems，功能区选项卡随之消失且用户无从知晓。一键诊断（diagnose.ps1 [5.5]）自动清除+报告；排查"加载项不见了"先查 Resiliency。
- **auto_check 以 JObject 并入返回值后，Data 序列化从匿名 ToString 变缩进 JSON**——探针断言（Contains("adv_type = x")）与 ExtractField（"key = value" 正则）须同步兼容 `"key": "value"` JSON 格式；这类断言假 FAIL 先看返回格式再怀疑产品。

### 6.10 沙箱/bash 派生环境：SystemRoot 大小写归一 → python 孙进程 winsock 10106；环境块大小写重复键 → StringDictionary「已添加项」（2026-09-12 Python 自愈批次真机定位）
- **现象**：msys bash 派生的 harness 里，产品代码派生的 pip 子进程稳定炸 `OSError: [WinError 10106] 无法加载或初始化请求的服务提供程序`（asyncio/_overlapped 导入期）；另一路 `ProcessStartInfo.EnvironmentVariables` 构建直接抛「已添加项。字典中的关键字:"PROGRAMW6432" 所添加的关键字:"ProgramW6432"」。同一解释器在 bash 直跑 pip 一切正常，极具迷惑性。
- **真根因**：①CRT `getenv` 大小写敏感——msys bash 把 `SystemRoot` 归一成全大写 `SYSTEMROOT`，winsock 初始化按规范大小写取值失配即 WSASYSNOTREADY；②环境块含大小写重复键时，.NET 大小写不敏感字典构建直接抛「已添加项」。手工 export 大小写变体（如 `COMSPEC` vs 系统原有 `ComSpec`）会复现并加重。
- **最小复现口诀**：PowerShell 里 `Remove-Item Env:SYSTEMROOT` 后 `python -c "import _overlapped"` 必现 10106；恢复变量即愈。环境类 bug 用「单变量移除/恢复」对照破案，比盲改快一个数量级。
- **改法（已落地 PythonWorkerHost）**：`SanitizeOwnEnvironment` 用 kernel32 `GetEnvironmentStrings` 原生直读去重（托管枚举本身会抛）+`CanonicalizeOwn` 把 SystemRoot/windir/SystemDrive/ComSpec 等重写为规范键名；`PreparePythonChildEnv` 统一 worker/RunCapture/RunProcess 三个子进程出口；pip 安装统一 `TryPipInstall` 经常驻 worker 的 subprocess 执行（worker 环境实证健康）。新增探针 `XaiProbe pyfix` 4 用例锁定该回归。
- **教训**：宿主环境是隐式输入。「工具闭环拿真实报错」要打到**最深层子进程的 stderr**（pip traceback 尾行才是真因），中间层包装错误（"安装失败（未知原因）"）会误导归因。

### 6.11 服务层 FinalRelease 共享身份 RCW（ActiveWorkbook/ActiveSheet/Worksheets.Item）→ 延迟引爆 InvalidComObjectException（v3.7.1.44 真机实证）
- **现象**：ud 套件新增 U3b（recommend_excel_chart）用例自身 PASS，但 U8 之后整轮 fatal「COM 对象与其基础 RCW 分开后就不能再使用」——引爆点与病灶不在同一用例。

### 6.12 同一工具多分支返回结构漂移 → 探针断言假 FAIL + AI 拿不到自检结果（v3.7.1.44）
- **现象**：ud 套件 U17~U21（原生瀑布/树状/旭日/排列/直方图）5 例假 FAIL，但 auto_check.verdict 全是 ok；同时 U22~U27 技巧图（漏斗/子弹/华夫/滑珠/蝴蝶/甘特）返回值里根本没有 auto_check。

### 2026-11-03 对抗性审查三视角收敛（MCP server 批次，R1-R4/Y1-Y6 修复）
- **CleanSchemaNode 剥 name 键不分级（🔴）**：schema 转换对任意层级剥 `name` 路由键，把 rename_excel_worksheet/add_excel_worksheet 的业务参数 `name` 也剥掉了——schema 与 required 自相矛盾。教训：**schema 路由键必须与业务参数名分层处理**（properties 值位置 = 属性定义层才剥）。单测 CleanSchemaNode_preserves_business_name_parameter 锁定。
- **SpawnedPids 进程名差集误杀窗口（🔴）**：GetProcessesByName 快照→COM 激活→差集 的窗口内第三方拉起的 EXCEL 会被记为 spawn 并在会话结束被 Kill——未保存数据丢失级。修复 = 从自身 COM 对象 Hwnd→GetWindowThreadProcessId 确定归因。**进程记账永远用确定 PID，不用名字差集**。WPS 兼容机 ProgID 指向 et.exe 时 "EXCEL" 名字查不到——同修。
- **stdio 主循环零兜底（🔴）**：客户端断连 IOException/畸形 LSP 帧/非法 JSON 标量都会炸出 Main 跳过 Cleanup → 泄漏 Visible=false 的 EXCEL。修复 = try/finally 强制 Cleanup + JObject is 判型 + 帧头 TryParse + 单帧 10MB 上限。**协议主循环的清理必须在 finally 里**。
- **传输层截断产出坏 JSON（🔴）**：Substring 拦腰砍 JSON 结构 + 可能劈开 UTF-16 代理对。修复 = 结构化降级（重建 {ok, transport_truncated, hint, data_preview}）。**任何限幅都要重新序列化，不能裸切字符串**。
- **JToken.Parse 默认 DateParseHandling（🟡）**：ISO 日期串 "2024-01-15" 进程内被转 DateTime 直写 Value2 变日期序列值，违反「写 ISO 日期先 NumberFormat=@"`」前提。修复 = JsonTextReader{DateParseHandling=None}（注意 JsonLoadSettings 无此属性，Newtonsoft 13.0.3 走 reader 层）。
- **Required 缺参返空串（🟡）**：缺 address → Range[""] → COMException → 误诊 EXCEL_COM_ERROR，恰是 M16 声称已修死的误诊路径复活。修复 = 缺参抛 ArgumentException 走 INVALID_ARGS。**空串缺参是错误码误诊的经典源头**。

### 2026-11-03 第二轮对抗审查（fix-the-fix，三视角复验收敛）
- **修 bug 修一半比不修更危险（🔴 教训）**：R2 把 PID 归因改对了（Hwnd→GetWindowThreadProcessId），但 Cleanup 强杀腿还是 GetProcessesByName("EXCEL")——WPS 宿主下归因到 et PID 永不命中 = 强杀静默失效。**修复必须全链路对齐：改了记账方式，消费方式必须同步改**（按 PID 直取 GetProcessById）。

- **JSON 嵌套三处同根坑（🟡）**：batch 数组非对象元素静默丢弃 / warning 无限幅透传 / 拦截回显全量 args——都是"内容未按载荷边界约束"。统一收敛：非对象回 -32600、warning 同款 preview、回显截 500 字符。
- **Replace 等文档防线要变代码防线（⚪→顺手修）**：XML 注释写"保留风险级别"但代码不校验，3 行等值校验 + fail-fast 异常收口（M17 守卫包装现网调用点零影响）。

### 2026-11-03 SQLite.Interop.dll 0x8007007E（WPS 32 位宿主 WebView2 初始化失败）
- **现象**：WPS ET（32 位）里加载项弹出「无法加载 DLL SQLite.Interop.dll: 0x8007007E」且 WebView2 二次初始化 success=False；Excel x64 宿主正常。
- **根因**：CodeBase 加载的 COM Add-in 场景，System.Data.SQLite 托管层按 AppDomain.BaseDirectory（= 宿主 EXE 目录）探测 SQLite.Interop.dll，而非托管 dll 所在目录。WPS ET 的 BaseDirectory = WPS office6（无 x86/x64 子目录）→ LoadLibrary 失败。Excel 宿主 BaseDirectory 探测恰好命中旧布局残留所以未暴露。
- **修复**：OnConnection 最早处（任何 SQLite 连接前）按进程位数用绝对路径 LoadLibrary 预加载 app/<arch>/x86|x64/SQLite.Interop.dll——已加载模块按名再请求直接命中，探测路径失效不再影响。通用双宿主，无宿主判断分支。
- **代码**：ExcelAiAddIn.cs OnConnection 顶部 preload 块 + Win32Native（kernel32 LoadLibrary, SetLastError）。
- **验证**：WPS ET 32 位真机会话 preload ok + WebView2 success=True 全链走通（00:27 会话）。

### 双分支工作流的修复提交血统断裂（M27 事故）
- 症状：审查修复提交只落在快照分支（batch-v3），master 无；「全量对齐」用 master 覆盖快照后两侧同时丢失，覆盖审计用例17 亮红才发现。
- 根因：修复用 `git checkout batch-v3` 后直接改文件提交——提交对象挂在快照血统上；master 后续对齐时以 master 树为准，抹掉快照侧独有内容。
- 规避：**任何代码修复先在 master 提交，再 cherry-pick 到快照分支推 main**；「对齐」方向永远 master→快照，禁止反向全树 checkout；每批收口跑真机 harness（覆盖审计是血统完整性的哨兵）。
- 恢复手段：`git cherry-pick -n <丢失提交>` + 冲突取语义正确侧 + 去重合并残留。

### 自检 plan 参数名必须对齐 verify 工具真实 schema（M27 A6 事故）
- 症状：新工具接 TryPlan 后，侧边栏每次写入都被自检判失败（fail-closed），MCP 直连却正常——因为 MCP 路径不经 AgentRunner/AutoVerifyMonitor。
- 根因：TryPlan 产出的 plan.Args 用了「自造参数名」（expected_address / expected_sheet），而 verify_write_result 只认 address/expected_values、verify_structure 只认 expected_sheet_exists/expected_sheet_absent。参数名对不上 → verify 工具 Required 抛错 → 自检失败 → 拦截写入。
- 规避：**接 TryPlan 前先去 ExcelVerifyService 读目标 verify 工具的 Required/Optional 参数名**；参数集与既有工具一致时直接复用其 TryPlan 分支（如 set_element 复用 TryPlanCellWrite）；新增 `AutoVerifyPlanContractTests` 白名单回归锁（plan.Args 键必须 ⊆ verify 工具接受集）。
- 同类风险：MCP 直连路径跳过自检，单测若只测 MCP 会漏——审查必须覆盖 AgentRunner 路径。

### 强杀 Office 宿主进程会取消勾选全部加载项（M27R2 事故）
- 症状：真机验证后用户报告「Excel/WPS 里所有加载项都不见了」。
- 根因：真机 harness 用 `taskkill /F /IM EXCEL.EXE` 强杀宿主，且多在加载项加载途中；Excel 判定这些加载项「启动崩溃」，逐个把 `LoadBehavior` 从 3 写回 2（等于取消勾选），并把 Analysis ToolPak 记入 Resiliency\DisabledItems。
- 规避：**收尾一律优雅关闭**——`CloseMainWindow()` → 等待退出；只有无主窗口的隐形 automation 孤儿实例才可强杀（它们不参与加载项加载）；强杀后立即复查 `HKCU\Software\Microsoft\Office\Excel\Addins\*` 的 LoadBehavior 并复位为 3。

### COM 注册必须按「位数视图 + 程序集版本」双维对齐（M27R2）
- 症状：部署新 DLL 后 Excel 里看不到选项卡；日志无 OnConnection。
- 两个根因叠加：①`InprocServer32\Assembly` 里登记的程序集版本与实际 DLL 不一致（.NET COM 激活要求标识精确匹配，不匹配直接加载失败）；②`HKCU\Software\Classes\CLSID` 是**按位数重定向**的——64 位视图与 32 位视图各存一份，用 64 位 PowerShell 写的值 32 位宿主（WPS ET）读不到（实测同键两视图一度分别为 3.9.1.1 / 3.8.3.0）。
- 规避：部署后必须**用 `reg add ... /reg:64` 与 `/reg:32` 分别写**，64 位视图指向 app\x64、32 位指向 app\x86，Assembly 版本取自 DLL 实际值；写完用 `reg query /reg:64|/reg:32` 双视图校验；`LoadBehavior` 也要分视图置 3。

### 用行号批量替换代码块时漏掉调用语句（M27R2 自伤）
- 症状：LSP 帧解析改造后，合规帧也拿不到任何响应。
- 根因：替换帧处理块时把 `HandleMessage(sb.ToString(), stdout);` 一并吃掉，正文读满却不派发。
- 规避：行号 splice 前后必须 diff 关键调用点（派发/返回/释放）是否仍在；改完立刻跑一次协议握手，不要只看编译通过。

### 草稿模式窗口必须取「源表 ∪ 草稿」并集（M27R2 数据丢失级）
- 症状：`start_draft → 改草稿 → diff_draft` 报「无变更」、`apply_draft` 只回写源表 UsedRange 那一小块，越界改动被静默丢弃且返回 ok:true。
- 根因：diff/apply 的比较窗与回写窗都取 `src.UsedRange` 的尺寸；源表只有 A1 时窗口=1×1。另外源值若直接用 `srcUsed.Value2`，源表仅 1 格会返回标量而非 matrix，越界格比较全部失真。
- 规避：窗口 = max(源表 UsedRange 尺寸, 草稿 UsedRange 右下角)；源值/公式必须**按并集区域显式取 Range**（`src.Range[src.Cells[1,1], src.Cells[rows,cols]]`）；改动后用「源表仅 A1、草稿改 B5」场景回归。

# 自检能力对标调研：本项目自检体系 vs 数据质量框架成熟方案（2026-09-19）

> 对标对象：Great Expectations / dbt tests / Soda Core（数据质量框架三巨头，自检领域事实标准）、ETL 测试平台（Datagaps ETL Validator）、数据可观测性理念（freshness/anomaly）。
> 本项目基线：v3.8.1.97（verify 家族 24 工具 + diagnose 2 + detect 1 + AutoVerifyPolicy 43 映射/100 豁免 + 读图自审 + 守恒对账 + 探针体系）。
> 与 2026-09-08《自检与工具完备度外部对标调研报告》的关系：该报告对标的是「工具面完备度」（对标 excel-mcp/openpyxl/Aspose），结论中的 verify_table/protection/hyperlink/image/freeze_panes 缺口**已全部补齐**；本报告对标的是「验证方法论」（对标 DQ 框架），聚焦自检的**组织方式与抽象层级**，两者互补不重复。

---

## 一、成熟方案核心方法论（检索实证）

### 1. 声明式期望与执行分离（GE 核心架构）
- **Expectation（期望）→ Expectation Suite（套件）→ Validator（执行器）→ Checkpoint（调度）** 四层分离：期望是「可执行、可版本控制的契约」——声明「这列非空/唯一/在枚举内/在区间内/行数在界内/最大日期距今 ≤1 天」，与执行调度彻底解耦 [ref: DEV Community GE vs dbt vs Soda 深度对比]
- **六大数据质量维度**作为期望分类法：完整性（not_null）/唯一性（unique）/有效性（in_set/between/regex）/准确性（交叉引用）/一致性（列对比较）/时效性（recency）[ref: agents 仓库 data-quality-frameworks 技能解析]
- **Data Docs**：验证结果自动渲染为 HTML 数据质量文档，结构化指标（unexpected_count/unexpected_percent/实际分布）而非只有 pass/fail [ref: 同上]

### 2. dbt tests：声明式 YAML + severity 分级
- schema.yml 里声明 `unique/not_null/accepted_values/relationships`，**severity 分级（error/warn）**——软失败不阻断但可见 [ref: DEV Community]
- 数据测试金字塔：Schema 测试（底，覆盖最广成本最低）→ 单列单测 → 跨表集成测试（顶）[ref: CSDN 技能解析]

### 3. Soda Core：SodaCL 声明语言 + 异常检测
- `missing_count(email) = 0` 这类人话断言；扫描结果 JSON 落盘可接 webhook 告警 [ref: DEV Community]

### 4. ETL 测试平台（Datagaps 等）的差异化能力
- **AI 辅助测试生成**（从映射文档自动生成测试，初始建测时间 -60%）、**DQ 评分与健康看板**（量化分数而非布尔）、跨管道编排 [ref: Datagaps 对比]

### 5. 数据可观测性三支柱
- **freshness（新鲜度）/volume 异常/anomaly 自动基线**——验证不只「这次对不对」，还有「和过去比变没变」[ref: calmops GE+dbt 观测性]

## 二、本项目自检体系现状盘点（代码事实，v3.8.1.97）

| 层 | 资产 | 说明 |
|---|---|---|
| 工具层 | verify_* 24 项 | write_result/formula/chart/dashboard/deep/conditional_format/data_clean/data_validation/freeze_panes/hyperlink/image/marker/merge/pivot/protection/sort_filter/sparkline/structure/table/cell_format——**操作级回读断言** |
| 诊断层 | diagnose_chart/diagnose_formula/detect_dashboard_data_readiness | 失败后根因归类+修复建议 |
| 策略层 | AutoVerifyPolicy（1338 行） | MappedPrimaryTools 43 工具写后自动自检；DocumentedWriteToolExemptions 100 条豁免（每条附理由，其中「确定性变换类」约 20 条挂账待转正）；ct_ 用户工具规则；覆盖审计（真机 harness/全功能巡检共用判定）；5 个一致性测试套件锁策略 |
| 闭环层 | 图表 auto_check 创建即自检 / 生成即试算 / 插入后巡检 / 读图自审（image_data_uri→AI 读图→diagnose/repair→复检） / 守恒对账（verify_dashboard_deep 数值守恒） | 「生成→自检→修复→复检」闭环 |
| 质量底盘 | basis 计算依据 / _口径.md / 探针体系（RealMachineVerify 119/WpsToolHarness full/ExamProbe 21 题/MacroChainProbe 15/ChartTestProbe 46） / gate | 工具面之外的工程级自检 |

**本项目独有且 DQ 框架不具备的**：操作级回滚语义下的写后断言（DQ 框架是管道批处理层，没有「这次 AI 操作写对了没」的问题域）；AI 读图视觉自审；确认门+撤销快照的组合。**没有一家外部 MCP/DQ 方案有这套**（9-08 报告结论至今成立且覆盖面已扩大）。

## 三、差距矩阵（按方法论抽象层级）

| # | 差距 | 本项目现状 | 成熟方案 | 定性 |
|---|---|---|---|---|
| 1 | **期望与执行未分离** | verify_* 是过程式工具级断言（每次调用传参验证） | Expectation Suite 声明式套件：一次定义、版本化、反复执行、可分享 | **最大差距** |
| 2 | **无数据质量维度分类法** | verify 维度按「工具产物」组织（图表/透视/清洗…） | 六维度分类法（完整性/唯一性/有效性/准确性/一致性/时效性）按「数据本身」组织 | 方法论差距 |
| 3 | **verdict 二态** | ok / fail（+issues 明细） | dbt error/warn 分级：软失败可见不阻断 | 小差距 |
| 4 | **无时效性检查** | 无 | recency 期望（日期列最大值距今天数上限）——表格数据「陈旧」是高频真实问题 | 小差距 |
| 5 | **验证结果无历史沉淀** | 即焚（一次性返回值） | GE 结果存储+Data Docs+质量趋势；Datagaps DQ 评分看板 | 中差距 |
| 6 | **无期望自动建议** | analyze_column_profile 只描述现状 | GE Profiler/suggestConstraints：扫数据→建议期望（枚举列建议 in_set、数值列建议 IQR 区间）→人确认后固化 | 中差距 |
| 7 | **豁免转正债** | 20+ 确定性变换工具「逐步补自动映射」挂账（AI 交接文档 §8 遗留项 1） | 「行数守恒/值集合守恒」是通用期望，可参数化复用 | 项目内债 |

| # | 借鉴点 | 对标来源 | 本项目落法 | 量级 |
|---|---|---|---|---|
| 1 | **区域期望套件**（核心借鉴） | GE Expectation Suite | 新增两工具：`manage_expectations`（对区域声明期望集：not_null/unique/in_set/between/regex/row_count/recency，JSON 落工作簿同目录 `_期望.json`，对齐 _口径.md 模式——声明与版本可分享）+ `verify_expectations`（按套件执行，出结构化结果：每条期望 verdict/实际值/违反数/违反样例 ≤5）。Core 纯逻辑 ExpectationEngine + 全套单测；与现有 verify_* 工具族互补（操作级 vs 数据级） | 2 天 |
| 2 | **severity 三级** | dbt error/warn | 新 verify 工具返回值加 warn 层（如空值率 5%~20%=warn 不算 fail、非空率 >95% 目标），现有 24 个 verify 的 verdict 语义不动（防回归），新工具先采用 | 0.5 天 |
| 3 | **期望自动建议** | GE Profiler/Deequ suggestConstraints | analyze_column_profile 返回值加 `suggested_expectations` 字段（枚举列→in_set、数值列→IQR 区间、日期列→recency），AI 转述给用户确认后经 manage_expectations 固化——与「口径记忆自动沉淀」同构，共用确认门 | 1 天 |

| 5 | **豁免转正提速** | 守恒即通用期望 | 用「变换后期望=变换前推导」参数化：行数守恒/值集合守恒/排序不变性三类通用断言可一次性把 transpose/date_normalize/number_pad/bankers_round 等 20+ 挂账工具批量转正（直接关掉 AI 交接文档 §8 遗留项 1） | 1 天 |

| 7 | **验证结果历史** | GE 结果存储 | 期望套件验证结果追加写入 `_期望历史.json`（≤30 条滚动），verify_expectations 返回「较上次的变化」——轻量版质量趋势，不做看板 | 0.5 天 |

### 不建议跟进的方向
- **管道调度/Checkpoint 编排**：GE Checkpoint 是 Airflow 生态产物，本项目单机交互式场景用不上（定时体检已在上一份调研 #3 覆盖，复用调度能力即可）
- **数据血缘/lineage**：工作簿场景无多级管道，投入产出不匹配
- **DQ 评分看板**：单用户单簿场景，结构化结果+报告已够

## 五、核心结论

1. **本项目的独特优势在「操作级自检」**：写后回读断言+自动映射+豁免审计+读图自审这套，是 DQ 框架完全不具备的问题域（它们管管道，我们管「AI 这次操作对不对」），护城河结论依旧成立且 9-08 后覆盖面翻倍（13→24 verify）。
2. **最大差距是「数据级期望的声明式抽象」**：verify 家族回答「这次操作的结果对不对」，但回答不了「这份数据本身可不可信且持续可信」——GE 用 Expectation Suite 二十行声明解决的问题，我们现在只能靠每次重新口述验证要求。
3. **最快见效组合：#1 期望套件 + #5 豁免转正**——前者补齐「数据可信」半边天并复用 _口径.md 生态，后者用同一套守恒期望清掉最大一笔项目内债（§8 遗留项 1），合计 ~3 天。

## 事故恢复方法学（重要，已真机验证）
1. **NEW-only 甄别法**：损伤文件先算「NEW 相对主副本(3.7.1.47)独有行数」。=0 → 整体取主副本零损失（ScriptRunner/ExternalBook/Workbook/PivotChart/UtilityTools 五文件即此）；>0 → 逐段手术（Dashboard 74 行/SuperBoard 100 行/ToolHost 111 行真实增量必须保 NEW）。
2. **降序 graft 铁律**：多段 graft 必须按 NEW 行号降序应用。升序时前面段膨胀（+7/+52 行）会把后面所有段行号推偏，曾致 139→219 错误反弹。
3. **插桩脚本三缺陷定性**（patch_logs_v3.py 事故根源，v4 已逐一修正）：①多行 catch 块重建时丢闭合 `}`；②单行 `try{..}catch{..}` 的 `{` 被误当 catch 块起点插进 try 体；③brace 配对计数被字符串字面量/注释内花括号欺骗。v4 改「行内插入不重建块」+ 剥离噪声计数 + 插入前后 depth 剖面逐行断言不一致即回滚。
4. **v4 残骸两类**：A 类孤立插值行（`$"[LogCover]..."` 无 Write 前缀）；B 类缺 `DiagnosticsLog.Write(` 前缀。均按「前一行是 catch 头或 {」定位修复。门面归属：Addin→DiagnosticsLog.Write，Excel/Core→AppLog.Warn。
5. **审查者视角真问题**：DiagnosticsLog.Append 自身 catch 内打 DiagnosticsLog.Write 会无限递归——自引用打点禁止，Ring 环缓存天然留痕即可。
6. **WPS full 隐藏语义依赖**：analyze_column_correlation 返回值缺 `strong` 字段会让 strong_pair_count 的 dynamic 反射 FAIL——返回值字段删除/改名须 grep 全库 dynamic 引用。
7. **先备份后动刀**已固化纪律：`_backup/src_snapshot_20260916_prelog/`（283 文件）在日志插桩前创建。
